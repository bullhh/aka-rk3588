同意你的方向：如果目标是提高“每秒完成识别和控制的帧数”，现在应该集中优化NPU。摄像头达到8～12 FPS本身够当前程序消费，继续把它提高到30 FPS不会直接提高检测帧率。

但我建议不要马上只改模型。当前最值得先做的是把Starry的NPU性能恢复到Linux水平。

### 当前耗时分布

Starry稳定数据是：

```text
RKNN运行       约88 ms
JPEG解码       约8.3 ms
RKNN输入       约0.59 ms
RKNN输出       约0.3 ms
后处理         约0.1 ms
其他           约8 ms
```

因此：

- 输入、输出、后处理基本不值得优先优化；
- NPU运行占绝大多数；
- 同一模型Linux只需约33.6 ms，Starry却需要约88 ms；
- 这约2.6倍的差距不能只归因于模型。

### 第一优先级：检查NPU时钟

这是当前最可疑、收益可能最大的地方。

Starry的NPU驱动目前：

- `GetFreq`直接返回0；
- `SetFreq`不做实际操作；
- `PowerOn/PowerOff`也没有实现。

见 [lib.rs](/home/szy/work/robot/tripod/tgoskits/drivers/npu/rockchip-npu/src/lib.rs:202)。

而仓库的RK3588 CRU驱动已经有NPU时钟读写能力，包括：

- `CLK_NPU_DSU0`
- `HCLK_NPU_ROOT`
- `PCLK_NPU_ROOT`
- `HCLK_NPU_CM0_ROOT`

见 [peripheral.rs](/home/szy/work/robot/tripod/tgoskits/drivers/soc/rockchip/rockchip-soc/src/variants/rk3588/cru/peripheral.rs:901)。

建议先完成：

1. Linux下读取NPU实际频率。
2. Starry启动时读取CRU中的NPU频率。
3. 比较两边是否分别运行在例如800 MHz和较低频率。
4. 在Starry中把NPU时钟稳定配置到Linux相同频率，再重复固定图片推理测试。

如果当前Starry的NPU实际只有300～400 MHz，那么把它恢复到800 MHz附近，就可能解释大部分 `88 → 33 ms` 的差距。

### 第二优先级：确认三个NPU核心真的同时工作

现在用户态传入的是：

```text
RKNN_NPU_CORE_0_1_2
```

但传入mask不等于硬件一定高效使用三个核心。需要记录：

```text
core_mask
active_cores
每个core的task_start/task_number
每个core的完成时间
```

当前驱动已经解析了 `subcore_task`，[ioctrl.rs](/home/szy/work/robot/tripod/tgoskits/drivers/npu/rockchip-npu/src/ioctrl.rs:197)，下一步应确认：

- `active_cores`是否确实为3；
- 三个核心是否同时启动；
- 是否有某个核心空任务；
- 是否实际在等待最慢的单个核心；
- 模型本身是否被RKNN正确切分到三个核心。

可以分别测试：

```text
core 0
core 1
core 2
core 0_1_2
```

如果三核和单核耗时接近，说明多核任务切分没有真正生效。

### 第三优先级：修正NPU计时

当前驱动返回的硬件耗时并不是真实测量值：

```rust
args.hw_elapse_time = (args.timeout / 2) as _;
```

见 [ioctrl.rs](/home/szy/work/robot/tripod/tgoskits/drivers/npu/rockchip-npu/src/ioctrl.rs:287)。

因此不能依赖 `hw_elapse_time` 判断NPU硬件到底运行了多久。应分别统计：

```text
任务准备时间
寄存器提交时间
NPU硬件等待时间
每个核心完成时间
缓存同步时间
整个ioctl时间
```

需要先回答一个关键问题：

```text
88 ms中，是NPU硬件真的运行了85 ms，
还是硬件已经完成，但驱动过晚发现？
```

### 第四优先级：把忙轮询改成中断等待

这项修改主要改善系统稳定性、CPU利用率和摄像头耦合，不一定直接让硬件推理从85 ms变成30 ms。

不过它仍然应该完成，因为当前：

```rust
while NPU未完成 {
    spin_loop();
}
```

会让CPU一直忙等。正确方式应是：

```text
提交NPU任务
→ 当前线程阻塞
→ NPU完成中断
→ 中断处理记录各核心完成状态
→ 唤醒提交线程
```

这样CPU可以同时处理控制、USB和JPEG，动作也会更稳定。

### 第五优先级：模型改成640×480

完成前面的驱动确认后，再实施你计划的 `640×480` 模型。

当前模型输入：

```text
640×640 = 409600像素
```

新模型输入：

```text
640×480 = 307200像素
```

理论输入计算量减少25%，而且摄像头原生就是640×480，可以消除上下黑边和无效区域计算。

合理预期是：

```text
如果Starry驱动仍为88 ms：
大约降到65～75 ms，提升到约14 FPS

如果先把Starry恢复到Linux的33 ms：
可能进一步降到25～30 ms
```

后者才是比较理想的结果。

### 推荐实施顺序

我建议下一阶段按以下顺序推进：

1. 固定图片RKNN-only测试，排除摄像头和JPEG。
2. 对比Linux与Starry的NPU实际时钟。
3. 确认三核任务分布和完成时间。
4. 修复NPU时钟、供电和核心初始化。
5. 修复真实硬件耗时统计。
6. 将忙轮询改成中断等待。
7. 训练并转换640×480模型。
8. 重新测试完整程序。

目标可以分两级：

```text
第一目标：Starry 88 ms → 接近Linux的33～40 ms
第二目标：640×480模型进一步达到25～30 ms
```

目前不建议优先做RKNN零拷贝、输出优化或后处理优化，因为这些环节总共不到约1.5 ms，远小于NPU本身的88 ms。
