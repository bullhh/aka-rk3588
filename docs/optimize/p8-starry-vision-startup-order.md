# Starry 视觉启动等待定位与优化

日期：2026-07-29
平台：Orange Pi 5 Plus，StarryOS SMP=8、WARN 日志，640×480 UVC，RKNN NPU core 0

## 结论

启动时几十秒的等待不在摄像头预热，也不在 RKNN 推理，而是以下顺序触发了 Starry 的 I/O 并发性能退化：

1. 先启动 UVC 流；
2. 再从 ext4 根文件系统读取 3.59 MB RKNN 模型。

将顺序改为“先读取并初始化模型，再打开 UVC”后，Starry 视觉就绪时间由 17.5～28.5 秒降到 1.46～1.52 秒。Linux 行为不受影响。

## 分段测试结果

| 环境与顺序 | 模型读取 | RKNN 初始化 | 摄像头打开 | 10 帧预热 | 视觉就绪总时间 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Linux，UVC 优先，冷启动 | 24.8 ms | 36.4 ms | 319 ms | 345 ms | 727 ms |
| Linux，UVC 优先，热启动 | 3.3～3.7 ms | 19.0 ms | 327 ms | 403～406 ms | 752～757 ms |
| Starry，UVC 优先，第 1 次 | 25.79 s | 413 ms | 1.12 s | 322 ms | 27.67 s |
| Starry，UVC 优先，后续 | 15.84～16.09 s | 354～415 ms | 1.01～1.16 s | 337～346 ms | 17.54～18.02 s |
| Starry，UVC 优先，模型位于 tmpfs | 25.3 ms | 370 ms | 833 ms | 317 ms | 1.55 s |
| Starry，模型优先，连续 3 次 | 405～428 ms | 131～139 ms | 507～550 ms | 364～427 ms | 1.46～1.52 s |

摄像头预热始终约 0.3～0.4 秒，因此终端停在 `Camera opened` 附近不代表摄像头仍在初始化；原程序此时正在慢速读取模型。

## 排除项

Starry 在摄像头关闭时读取同一 ext4 文件：

- `dd` 使用 4 KiB～4 MiB 块读取均只需 0.47～0.56 秒，约 6.4～7.6 MB/s；
- ext4 复制到 tmpfs 不到 1 秒；
- tmpfs 中的模型在 UVC 已启动时也只需 25.3 ms。

以下用户态读取改写均未改善 UVC 启动后的 ext4 慢读，已撤销：

- `fread` 改为 POSIX `open/fstat/read`；
- 读取前预触碰大模型缓冲区；
- 使用 64 KiB 中转缓冲区分块读取。

因此问题不是模型大小、存储介质带宽、`fread` API 或读取块大小本身，而是 Starry 当前 UVC 流与 ext4/SDHCI I/O 同时工作时的调度或 I/O 路径竞争。

## 最小修复

正式程序和 `test-yolo` 均调整为：

```text
机械臂/底盘初始化
  -> 读取模型并完成 RKNN 初始化
  -> 打开 UVC 并启动视频流
  -> 预热摄像头
  -> 进入识别与控制循环
```

只改变一次性初始化顺序，不改变模型、采集分辨率、推理过程、机械臂动作或底盘控制。摄像头打开失败时会通过现有清理路径释放已经创建的 RKNN 上下文。

## 后续可优化点

1. Starry 内核侧继续分析 UVC/USBFS 活跃时 ext4/SDHCI 吞吐下降的原因。应用顺序已规避启动等待，但底层并发问题仍存在。
2. Starry 摄像头打开约 0.5 秒，Linux 约 0.3 秒；可继续检查描述符解析和重复接口 claim，但绝对收益仅约 0.2 秒。
3. Starry 单独读取模型约 0.4 秒，Linux 为 3～25 ms；可优化 ext4/SDHCI 读取，但当前已不是启动主要瓶颈。
4. `unsupported descriptor subtype` 和 `attempt to claim already-claimed interface` 是兼容性提示，本轮实测中没有导致打开失败，也不是几十秒等待的来源。
