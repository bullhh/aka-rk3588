# Linux 与 StarryOS 正式流程前台复测（2026-07-30）

## 1. 修正说明

上一版测试把程序输出重定向到板端 ext4 日志文件。StarryOS 下 UVC 与 ext4/SDHCI
并发会产生额外停顿，因此原先得到的 **7.48 FPS** 不是正式程序正常前台运行的性能，
不能继续引用。

本次改为：

- 程序始终在串口前台运行；
- 日志由本机串口终端保存，板端不写测试日志；
- Linux 重复 3 次相同完整控制路径；
- StarryOS 使用两次独立串口前台样本交叉验证，其中一次为用户现场运行，一次为
  Codex 重新启动系统后的完整流程；
- StarryOS 使用 SMP=8、`Warn` 日志和 RKNN core 0。

## 2. 测试路径

车轮架起时无法靠物理位移自然完成捡球，因此测试钩子只负责推进状态：

1. 运行 30 秒真实 `CHASE_BALL`，执行 UVC 取帧、JPEG 解码、RKNN 推理、检测、
   Feetech 通信和车轮控制；
2. 推进到 `PICK_BALL`，执行完整真实机械臂夹球轨迹；
3. 模拟持球后运行 10 秒真实找桶识别和车轮控制；
4. 推进到 `PUT_BALL`，执行完整真实放球轨迹并正常退出。

测试钩子不改变被测视觉和控制逻辑，测试后已从源码中删除。

## 3. 结果

### 3.1 Linux

三次有效完整流程的 30 秒追球阶段均处理 900 帧：

| 运行 | 处理帧数 | 有效帧率 | 完整流程结果 |
| --- | ---: | ---: | --- |
| 1 | 900 | 30.00 FPS | 成功 |
| 2 | 900 | 30.00 FPS | 成功 |
| 3 | 900 | 30.00 FPS | 成功 |

Linux 已达到摄像头设定的 30 FPS 上限。稳定窗口中 `rknn_run` 约 12.0 ms，JPEG
解码约 4.6～4.9 ms，取帧等待约 15.7～16.1 ms。

首次额外运行曾在 Feetech 初始化阶段发生一次 `rx timeout waiting for header`，尚未
进入主循环，因此未计入性能样本。

### 3.2 StarryOS

两次前台样本与用户现场现象一致：

| 样本 | 第一个 10 秒窗口 | 后续稳定窗口 | 30 秒含冷启动平均 |
| --- | ---: | ---: | ---: |
| 用户现场运行 | 8.87 FPS | 15.62、16.19 FPS | 13.56 FPS |
| 重新启动后复测 | 7.13 FPS | 16.40、约 16.0 FPS | 13.20 FPS |
| 合并结果 | 约 8.0 FPS | **约 16.05 FPS** | **约 13.38 FPS** |

复测完整执行了夹球和放球轨迹并以返回码 0 退出。第 3 个性能窗口在打印前包含阻塞式
机械臂动作，不能直接使用它打印的窗口时长计算 FPS；表中按进入机械臂动作前的 30 秒
追球阶段处理帧数计算。

StarryOS 稳定追球阶段的代表性耗时约为：

| 阶段 | 每帧耗时 |
| --- | ---: |
| 取帧等待 | 29.1 ms |
| JPEG 解码 | 8.9 ms |
| `rknn_run` | 15.7 ms |
| 其他复制、输入输出、后处理和控制 | 约 6～8 ms |
| 总帧时间 | 约 62.3 ms |

### 3.3 找桶阶段

重新复测的找桶窗口为 8.72 FPS，`rknn_run=0`，JPEG 解码 35.51 ms，另有较大的
未归类等待。这里只取得一个完整流程样本，尚不足以把 8.72 FPS 当成稳定均值，但它
说明找桶路径仍可能存在重复 JPEG 解码及 StarryOS 调度停顿，需要独立复测。

## 4. 最终结论

1. 用户看到的 **12～16 FPS 是正常且可复现的**：StarryOS 冷启动后首个窗口约
   7～9 FPS，稳定后约 16 FPS；若把冷启动窗口也算入前 30 秒，平均约 13.4 FPS。
2. 原先 **7.48 FPS 的结论无效**，根因是测试方法在板端持续写 ext4 日志，额外触发
   StarryOS 的 UVC 与存储并发问题。
3. Linux 完整追球流程稳定为 30 FPS；StarryOS 稳态约为 Linux 的 53.5%，主要差值
   仍在约 29 ms 的取帧等待以及较高的系统调度/驱动开销，而不是模型纯推理单项。
4. 性能对比必须使用串口前台运行或在主机侧抓取串口，不能把高频日志重定向到
   StarryOS 的板端文件系统。
