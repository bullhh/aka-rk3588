# 三足捡球机器人性能优化总结

## 1. 文档范围与当前结论

当前版本已经在 RK3588 的 Linux 和 StarryOS 上完成找球、追球、夹球、找桶、
对齐桶和放球闭环。近期优化的主要结果如下：

- 历史同场景模型 A/B 中，StarryOS 使用 ReLU 模型时达到 **14.11 FPS**；该结果
  可以证明 ReLU 相对 SiLU 的收益，但不能代表所有正式运行场景。
- 2026-07-30 的串口前台复测中，Linux 的正式追球阶段稳定为 **30.00 FPS**，
  StarryOS 稳态为 **约 16.05 FPS**。性能结论只统计进入稳定运行后的完整 10 秒
  窗口。
- 在严格固定输入测试中，640×480 模型相对 640×640 模型使 StarryOS 的
  NPU 时间降低 **78.9%**；正式 ReLU 模型又相对同尺寸 SiLU 模型降低
  **23.55%**。
- UVC 用户态收帧策略优化后，StarryOS UVC-only 从约 **11 FPS** 提高到
  **27.6 FPS**。去除底盘和机械臂的视觉组件基准为 **16.01 FPS**，正式流程
  稳态复测同样约 **16.05 FPS**。
- 调整初始化顺序后，StarryOS 从启动程序到视觉就绪由 **17.54～27.67 秒**
  降至 **1.46～1.52 秒**。

## 3. 优化前基线

### 3.1 Linux 640×640 基线

Linux 使用 640×480 MJPEG 摄像头和 640×640 INT8 模型。放球完成后的两个
稳态窗口共 20.03 秒：

| 指标 | 基线 |
| --- | ---: |
| 摄像头帧率 | 29.87 FPS |
| 有效处理帧率 | 26.31 FPS |
| 单帧平均耗时 | 37.99 ms |
| JPEG 解码 | 3.47 ms |
| letterbox | 0.125 ms |
| RKNN 推理 | 33.56 ms |
| 控制 | 0.116 ms |
| 被新帧覆盖 | 70 / 598，11.7% |

RKNN 推理约占单帧时间的 88%，是 Linux 基线的主要瓶颈。

### 3.2 StarryOS 640×640 基线

StarryOS `Warn` 构建采集 9 个稳态窗口，共 91.01 秒：

| 指标 | Linux | StarryOS | StarryOS 相对情况 |
| --- | ---: | ---: | ---: |
| 摄像头帧率 | 29.87 | 7.83 FPS | 26% |
| 有效处理帧率 | 26.31 | 6.32 FPS | 24% |
| 单帧平均耗时 | 37.99 | 157.79 ms | 4.15 倍 |
| JPEG 解码 | 3.47 | 8.30 ms | 2.39 倍 |
| RKNN 推理 | 33.56 | 88.24 ms | 2.63 倍 |
| 摄像头等待 | 约 0.20 | 47.91 ms | 明显变长 |

初始问题不是单一的“摄像头慢”或“NPU 慢”，而是 UVC 交付、NPU 等待、CPU
解码和调度均有差距。因此后续先补齐分阶段统计，再逐项做隔离测试。

原始基线见 [Linux P0 基线](./p0-performance-baseline.md) 和
[Linux/StarryOS P0 对比](./p0-linux-vs-starry-baseline.md)。

## 4. 已保留的优化

### 4.1 建立 10 秒性能窗口并限制高频日志

对应提交：`6636b2c perf(vision): improve Starry camera throughput`。

修改内容：

- 使用 `CLOCK_MONOTONIC` 统计每 10 秒的采集、处理和阶段耗时。
- 输出单帧平均值、P50、P95、最大值，以及 UVC 等待/复制、JPEG、
  letterbox、RKNN 输入/运行/输出、后处理、释放和控制耗时。
- 球位置、桶位置和轮速等连续状态默认每秒最多打印一次；错误、重试、超时和
  状态切换仍立即打印。
- 机械臂步骤只在步骤变化时打印，不再每个 50 ms 控制周期重复输出。

影响：

- 这是测量和可观测性优化，使后续瓶颈定位有可复核数据。
- 降低串口输出和格式化开销，尤其避免状态标签交替时退化为逐帧打印。
- 没有做“只改变日志频率”的严格吞吐 A/B，因此不虚构 FPS 提升比例。
- 调试瞬时行为时仍可通过 `AKA_STATE_LOG_INTERVAL_MS=0` 恢复逐帧日志。

### 4.2 机械臂固定周期与基于时间的平滑轨迹

对应提交：`1f9ff6c fix(lekiwi): stabilize arm control timing`。

优化前，控制循环完成一轮 Feetech 通信后再固定 `usleep(50000)`，实际周期为
“通信耗时 + 50 ms”。通信时间波动会直接改变动作速度，S 曲线又按循环次数推进，
容易出现忽快忽慢；残差较小时还可能直接跳到目标角度。

优化后：

- 使用单调时钟维持绝对 50 ms 控制节拍，通信耗时包含在周期内。
- S 曲线按真实经过时间推进，不再假设每次循环恰好等长。
- 普通动作每周期最大 0.75°，即不超过 15°/s。
- HOME 回位每周期最大 1.25°，即不超过 25°/s。
- 夹爪每周期最大 2°，即不超过 40°/s。
- 若某周期因调度或通信变长，动作允许整体延长，不在下一周期追赶跳变。

影响：机械臂动作速度上限可预测，调度抖动不会转换为突跳，启动和回 HOME 更安全。
本项主要改善流畅度和稳定性，没有同轨迹加速度计或视频测量数据，因此不以 FPS 或
百分比表达收益。

### 4.3 机械臂动作期间暂停 UVC

对应提交：`babdf94 fix(lekiwi): pause camera during arm motion`，流句柄重建逻辑随后
包含在 `6636b2c` 中。

夹球和放球轨迹执行期间，主循环不会使用视觉帧，但原程序仍让 UVC 持续传输，
与 Feetech USB CDC 共用 USB 路径。现在进入 `PICK_BALL` 或 `PUT_BALL` 前停止
UVC 流，动作完成后在同一设备句柄上重建 stream handle 并恢复采集。

实测结果：

| 项目 | 数据 |
| --- | ---: |
| 夹球前暂停 UVC | 598.7 ms |
| 夹球后恢复 UVC | 709.4 ms |
| 恢复后的稳态有效帧率 | 13.50、13.47 FPS |
| 旧 stream handle 暂停 20 s 后恢复 | 曾黑屏约 35 s |
| 重建 stream handle 后恢复 | 首帧立即到达，UVC-only 27.8 FPS |

影响：动作期间不浪费 UVC 带宽，减少摄像头与舵机通信竞争，并避免恢复后的陈旧
URB/端点状态。代价是每次动作切换约 0.6～0.7 秒，但夹球/放球轨迹本身约十几秒，
且此时不需要视觉，因此该代价可接受。

### 4.4 模型输入从 640×640 改为 640×480

优化方向是让模型静态输入与摄像头原生分辨率一致。保留原检测权重，只重塑 ONNX
输入和 YOLO 网格，并用 Roboflow 官方验证集 684 张图片重新进行 INT8 校准。

结构变化：

| 项目 | 640×640 | 640×480 | 变化 |
| --- | ---: | ---: | ---: |
| 输入元素 | 1,228,800 | 921,600 | -25% |
| YOLO 候选位置 | 8,400 | 6,300 | -25% |
| 640×480 图像补边 | 上下各 80 px | 无 | 消除无效区域 |
| RKNN 大小 | 4,676,305 B | 4,107,848 B | -12.16% |

严格固定输入 A/B：

| 系统 | 640×640 | 640×480 SiLU | NPU 时间降低 |
| --- | ---: | ---: | ---: |
| Linux | 42.05 ms | 16.22 ms | 61.4% |
| StarryOS | 93.98 ms | 19.84 ms | 78.9% |

StarryOS 完整链路代表性对比：

| 指标 | 640×640 基线 | 640×480 首轮稳态 | 变化 |
| --- | ---: | ---: | ---: |
| 摄像头帧率 | 7.83 | 8.28 FPS | +5.7% |
| 有效处理帧率 | 6.32 | 8.38 FPS | +32.6% |
| 单帧平均耗时 | 157.79 | 119.36 ms | -24.4% |
| JPEG 解码 | 8.30 | 8.34 ms | 基本不变 |
| RKNN 推理 | 88.24 | 22.71 ms | -74.3% |

固定输入结果是严格 A/B；完整链路数据来自一个 10.03 秒稳态窗口，场景和 UVC
调度仍会影响结果，因此只作为实机收益证据。新模型已在 Linux 和 StarryOS 完成
真实闭环，控制坐标仍为 640×480，不需要缩放停车、夹球和桶参数。

详见 [640×480 模型结果](./p2-640x480-model-result.md)。

### 4.5 改用同步 UVC 取帧并固定 30 FPS

这项优化没有修改分辨率、MJPEG 格式或 USB/xHCI 驱动，只修改了两件事：

1. libuvc 把完整图片交给主程序的方式；
2. 摄像头是否可以因自动曝光而主动降低帧率。

#### 4.5.1 先区分三种帧率

摄像头通过以下接口协商为 `640×480 MJPEG @ 30 FPS`，理论上每 33.3 ms
产生一帧：

```cpp
uvc_get_stream_ctrl_format_size(
    devh_, &ctrl_, UVC_FRAME_FORMAT_MJPEG, 640, 480, 30);
```

当前实测数据分别表示：

| 含义 | Linux | StarryOS |
| --- | ---: | ---: |
| 摄像头配置帧率 | 30 FPS | 30 FPS |
| UVC-only 最快取帧 | 约 29.8 FPS | 约 27.6～28.6 FPS |
| 去除底盘/机械臂的视觉组件基准 | 约 30 FPS | 16.01 FPS |
| 当前正式流程稳态追球 | 30.00 FPS | 约 16.05 FPS |

正式程序稳态日志中的 `camera` 约为 16～17 FPS，不表示摄像头传感器只产生相同
数量的帧。`captured_frames_` 只在主线程成功调用一次 `getFrame()` 后加一；主线程
还要串行执行 JPEG 解码、NPU 推理和控制，所以稳态每秒实际处理约 16.05 帧。摄像头
在此期间仍可按约 30 FPS 产生数据，未被程序取走的中间帧不会排队等待处理。

例如，当前 StarryOS 稳态完整处理一帧约需 62.3 ms：

```text
 0 ms：摄像头产生第 1 帧，主线程取走并开始处理
33 ms：摄像头产生第 2 帧，主线程仍在处理第 1 帧
62 ms：主线程完成本轮，并取得此时可用的最新完整帧
66 ms：摄像头产生第 3 帧
```

主线程不会回头处理已经过时的中间帧，而是在下一轮取得当前可用的最新完整帧。对
机器人实时控制来说，这种“跳过旧帧、处理最新画面”的策略比积压旧画面更合适，
否则程序虽然每一帧都处理了，控制结果却可能落后现场几秒。

因此，当前日志中的 `camera` 更准确的含义是“程序成功取帧率”；摄像头和 UVC
链路的最大交付能力应通过 UVC-only 测试判断。

#### 4.5.2 优化前：图片需要经过回调线程转交

旧实现使用：

```cpp
uvc_start_streaming(devh_, &ctrl_, frame_cb, this, 0);
```

流程为：

```text
摄像头 → USB/libusb → libuvc 组装完整图片
       → 等待回调线程运行
       → 回调复制到 pending_data_ 单槽缓冲区
       → 条件变量唤醒主线程
       → 主线程再复制一次
       → JPEG 解码、NPU 推理和控制
```

这相当于快递已经送到站点，但必须先等中转人员把它放进一个只有一格的柜子，再通知
主程序取件。StarryOS 同时运行 RKNN 时，NPU 驱动及辅助线程存在忙等，回调线程容易
得不到及时调度。新图片继续到达时，libuvc 或用户单槽缓冲区中的旧图片会被更新，
所以底层已经收到约 30 帧，主程序却只能看到约 11 帧。

下面是一个用于说明机制的简化时间线。假设摄像头按 30 FPS 工作，但回调线程因
调度延迟约 90 ms 后才获得运行机会：

```text
 0 ms：第 1 帧在 USB/libuvc 中完成，等待回调线程
33 ms：第 2 帧完成，完整帧状态更新
66 ms：第 3 帧完成，完整帧状态再次更新
90 ms：回调线程终于运行，只能把当前可见的最新帧交给主程序
```

摄像头和 USB 在这 90 ms 内没有停止，丢失发生在“完整图片交给用户回调”的中转
阶段。因此旧实现看到约 11 FPS，并不等于摄像头或 USB 只能工作在 11 FPS。

旧流程还需要两次 MJPEG 复制、mutex、条件变量和一次额外线程唤醒，但这些只是次要
开销；主要问题是主程序必须等待回调线程先获得调度。

#### 4.5.3 优化后：主线程直接等待完整图片

新实现以无用户回调方式启动流：

```cpp
uvc_stream_open_ctrl(devh_, &strmh_, &ctrl_);
uvc_stream_start(strmh_, nullptr, nullptr, 0);
```

主线程需要图片时直接调用：

```cpp
uvc_stream_get_frame(strmh_, &frame, timeout_ms * 1000);
memcpy(mjpeg_buf, frame->data, frame->data_bytes);
```

流程缩短为：

```text
摄像头 → USB/libusb → libuvc 组装完整图片
       → 直接唤醒等待图片的主线程
       → 复制一次
       → JPEG 解码、NPU 推理和控制
```

这里的“同步”只表示主线程直接阻塞等待下一张完整图片。USB 和 libusb 仍在后台接收
数据，并没有改成“主线程调用后摄像头才开始拍照”。主线程等待时会睡眠，不会空转
占满 CPU。

实际结构仍然是：

```text
后台：摄像头持续拍照，USB 持续传输，libusb 处理 USB 事件，libuvc 组装完整图片
前台：主线程处理上一帧；需要新帧时，直接等待或取得 libuvc 的最新完整图片
```

`uvc_stream_get_frame()` 更像“到取件窗口领取已经在运输的下一件快递”，而不是
“按下按钮后快递才从发货地出发”：

- 调用时如果已经有新完整帧，接口可以直接返回；
- 如果下一帧尚未组装完成，主线程进入阻塞等待；
- 阻塞期间内核可以调度 libusb 事件线程和其他任务，等待线程不会持续消耗 CPU；
- 完整帧到达后，libuvc 唤醒主线程，主线程只复制一次便进入解码和推理。

所以“同步取帧”同步的是**主线程取得完整帧的接口**，并没有把摄像头、USB 或
libusb 的后台传输改成串行按需启动。

新实现删除了用户回调、`pending_data_`、mutex、条件变量和一次额外复制。更重要的
是，它删除了“回调线程必须先得到调度”这一中转步骤，正好避开 StarryOS 当前较弱的
线程调度环节。

#### 4.5.4 为什么还要限制自动曝光降帧

只请求 30 FPS 仍不够。摄像头在光线不足时可能把每帧曝光从约 33 ms 延长到约
100 ms，并把实际产帧率降到约 10 FPS。Linux 已实测复现这种行为。

当前增加：

```cpp
uvc_set_ae_priority(devh_, 0);
```

它保留自动曝光，但不允许自动曝光通过延长帧间隔来降低帧率。因此摄像头继续按约
30 FPS 产生图像。代价是极暗环境下不能通过降到 10 FPS 获得三倍曝光时间，画面
可能更暗或噪声更多，应优先改善现场照明。如果摄像头不支持该控制，程序只打印提示
并继续运行。

#### 4.5.5 为什么提升明显，但完整程序仍不到 30 FPS

这次同时移除了两个限制：

- 摄像头源头不再因自动曝光从 30 FPS 降到约 10 FPS；
- 已被 USB 收到的完整帧不再卡在回调线程中，主线程可以直接取得。

因此 UVC-only 的提升不是 USB 速度变快，而是程序终于取得了 USB 原本已经收到的
大部分图片：

| 场景 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| StarryOS UVC-only | 约 11 FPS | 27.6 FPS | 约 2.5 倍 |
| StarryOS 当时的正式视觉链路 | 8.38 FPS | 13.1～13.5 FPS | 约 +60% |
| Linux UVC-only | 30 FPS | 29.8 FPS | 无实质回退 |

完整程序仍然串行执行：

```text
取帧 → JPEG 解码 → NPU 推理 → 后处理 → 控制 → 再取下一帧
```

历史同场景窗口中，一轮约包含 21～24 ms 取帧等待、8.5～8.7 ms JPEG 解码、
35～37 ms RKNN 运行和数毫秒控制，总计约 70～75 ms：

```text
1000 ms ÷ 75 ms ≈ 13.3 FPS
```

所以约 28 FPS 表示摄像头链路单独运行时的供帧能力，并不保证完整程序达到同样吞吐。
最新串口前台复测的 StarryOS 稳态约 16.05 FPS；同步取帧解决了旧回调中转造成的
采集链异常变慢问题，但没有实现采集与推理并行。测试时不能把日志重定向到板端 ext4，
否则会触发 UVC 与存储并发停顿并得到失真的低帧率。

当前稳态一轮约为 62.3 ms，对应：

```text
1000 ms ÷ 62.3 ms ≈ 16.05 FPS
```

性能日志中：

- `capture_wait`：主线程等待下一张完整图片的时间；
- `capture_copy`：把该图片复制到业务缓冲区的时间；
- `effective_fps`：完整程序每秒实际处理的帧数，是最终性能指标。

该修改在 Linux UVC-only 下仍为约 29.8 FPS，没有明显回退。机械臂长动作前继续
暂停 UVC，动作后重建 stream handle，避免长时间暂停后黑屏；本次没有修改
StarryOS USB/xHCI 内核代码。

详见 [StarryOS UVC 优化结果](./p3-starry-uvc-result.md)。

### 4.6 正式程序保持 NPU core 0，不插入人工等待

隔离测试曾发现，StarryOS 连续 NPU 推理会挤压 USB 完成链；在诊断程序的推理后
加入一次极短 `usleep()`，UVC 可从 11.73 FPS 恢复到 29.66 FPS。但诊断程序使用
固定 RGB 输入，没有 JPEG 解码和完整控制，不能直接代表正式程序。

随后用正式程序、实球画面和车轮控制逐项测试：

| NPU 配置 | 人工等待 | 稳态有效帧率 | 结论 |
| --- | ---: | ---: | --- |
| core 0 | 0 µs | 平均 13.28 FPS | 当前最优基线 |
| core 0 | 1～2 µs | 约 13.0～13.5 FPS | 波动范围内，无稳定提升 |
| core 0 | 3 µs | 约 13.0～13.2 FPS | 略降 |
| core 0 | 5 µs | 11.19～11.56 FPS | 实际调度约 50 ms，下降约 14% |
| core 0/1/2 | 0 µs | 12.92～13.21 FPS | 没有提升 |

因此正式程序不保留 `usleep()`，StarryOS 默认固定 RKNN core 0。该结论防止把
隔离测试中有效的诊断手段误用为正式优化。详见
[正式程序 NPU 等待测试](./p6-starry-formal-program-test.md)。

### 4.7 使用正式训练的 ReLU 模型

在完整 Roboflow 数据集上，将网络内部 56 个卷积激活由 SiLU 改为 ReLU，重新
训练、导出 640×480 ONNX，并用全部 684 张验证图片做 RKNN INT8 校准。

数据集：训练 11,268 张、验证 684 张、测试 285 张。最终部署模型来自第 4 个
epoch 的最佳权重；第 5 个 epoch 后指标开始回落，没有继续无效训练。

精度影响：

| 模型 | 测试集 Precision | Recall | mAP50 | mAP50-95 |
| --- | ---: | ---: | ---: | ---: |
| SiLU | 0.93495 | 0.90303 | 0.92238 | 0.72285 |
| ReLU | 0.94193 | 0.89173 | 0.92463 | 0.71262 |
| 变化 | +0.00698 | -0.01130 | +0.00225 | -0.01023 |

ReLU 不是精度无损替换：mAP50 略升，但 Recall 和 mAP50-95 略降。量化前后检查
中，测试集前 50 张的最高置信度平均绝对误差为 0.00508，最高框平均 IoU 为
0.89819，50 个 FP32 阳性全部在 INT8 中保留。

性能结果：

| 环境 | SiLU | ReLU | NPU 时间降低 |
| --- | ---: | ---: | ---: |
| Linux，固定输入 | 15.83 ms | 11.98 ms | 24.30% |
| StarryOS，固定输入 | 18.04 ms | 13.79 ms | 23.55% |
| StarryOS 正式程序 | 35.12 ms | 26.41 ms | 24.8% |

StarryOS 正式程序同场景 10 秒窗口：

| 模型 | 各稳态窗口 | 平均有效帧率 |
| --- | --- | ---: |
| SiLU | 13.39、13.66、13.89 | 13.65 FPS |
| ReLU | 14.29、13.90、14.13 | 14.11 FPS |

完整链路有效帧率提高 **3.4%**，小于纯 NPU 的约 24% 提升，因为 UVC 等待、
JPEG 解码和控制仍占用大量时间。模型大小从 4,107,848 B 减至 3,588,424 B，
降低 12.64%。ReLU 已完成一次无假检测、无放宽配置的真实夹球和放球闭环；板端
保留 SiLU 备份，后续若远距离小球召回明显下降可立即回滚。

详见 [ReLU 正式训练与测试](./p7-relu-formal-training-result.md)。

### 4.8 模型先于摄像头初始化

原程序顺序为：先打开并启动 UVC，再从 ext4 读取 RKNN 模型。StarryOS 下二者
并发时，读取 3.59 MB 模型会从正常约 0.4 秒恶化到 15～26 秒。终端看起来停在
摄像头相关日志之后，实际等待的是模型读取。

隔离测试：

- 摄像头关闭时，StarryOS 用不同块大小读取模型只需 0.47～0.56 秒。
- 模型复制到 tmpfs 后，即使 UVC 已启动，读取也只需 25.3 ms。
- 改用 POSIX `read`、预触碰内存和 64 KiB 中转缓冲均无效。

最终只调整初始化顺序：

```text
机械臂/底盘初始化
→ 读取模型并完成 RKNN 初始化
→ 打开 UVC 并启动视频流
→ 预热 10 帧
→ 进入控制循环
```

以下时间从开始读取 RKNN 模型计到摄像头完成 10 帧预热、可以进入识别控制循环。
StarryOS 使用 SMP=8、`Warn` 日志、RKNN core 0，模型为 3.59 MB：

| StarryOS 初始化方式 | 模型读取 | RKNN 初始化 | 摄像头打开 | 10 帧预热 | 视觉就绪总时间 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 修改前：UVC 优先，第 1 次 | 25.79 s | 413 ms | 1.12 s | 322 ms | **27.67 s** |
| 修改前：UVC 优先，后续 | 15.84～16.09 s | 354～415 ms | 1.01～1.16 s | 337～346 ms | **17.54～18.02 s** |
| 修改后：模型优先，连续 3 次 | 405～428 ms | 131～139 ms | 507～550 ms | 364～427 ms | **1.46～1.52 s** |

修改后，常规重复启动由 **17.54～18.02 秒** 降到 **1.46～1.52 秒**，减少约
**16.0～16.6 秒（91.3%～91.9%）**；与修改前第一次 27.67 秒相比，减少约
**26.2 秒（94.7%）**。主要收益来自模型读取由 15.84～25.79 秒恢复为
405～428 ms。Linux 仍约 0.7 秒，没有功能回退。当前完整程序摄像头预热 10 帧；
`test-yolo` 的独立测试路径仍预热 20 帧。

该修改是用户态最小规避：不改变文件读取实现、模型和运行逻辑。StarryOS 中
UVC 活跃时 ext4/SDHCI 吞吐异常的底层问题仍需在内核继续定位。

详见 [StarryOS 视觉启动顺序](./p8-starry-vision-startup-order.md)。

## 6. 已测试但未保留的方案

只保留经过实测有效的最小修改，以下尝试均已撤销或没有进入正式流程：

- 修改 xHCI 周期端点 interval：URB 完成频率变化，但完整 MJPEG 和正式帧率无提升。
- 修改 xHCI Block Event Interrupt：帧率无变化。
- 独立采集线程原型：Linux 下不稳定，可能不交付帧且退出阻塞；未保留。
- 正式程序在每次 NPU 后 `usleep(1～3 µs)`：没有可重复收益。
- `usleep(5 µs)`：StarryOS 实际调度约 50 ms，正式帧率下降约 14%。
- NPU core 0/1/2：正式程序 12.92～13.21 FPS，未优于 core 0。
- UVC 活跃时改用 POSIX `read` 读取模型、预触碰缓冲、64 KiB 分块：启动慢读不变。
- 640×480 一轮低学习率微调：独立测试集精度下降，未采用该权重。

这些结果很重要：它们限制了后续搜索范围，也避免把隔离程序的局部现象当作正式程序
收益。

## 7. 当前影响与剩余瓶颈

### 7.1 当前正面影响

- Linux 和 StarryOS 使用同一用户态程序、模型和 640×480 控制坐标。
- 模型和 UVC 单项优化均已在 StarryOS 得到可重复收益，程序已通过真实闭环；最新
  前台复测稳态约 16.05 FPS。
- 模型输入不再计算上下补边，NPU 计算量和模型体积均下降。
- 摄像头单独采集接近 30 FPS，Linux 无明显回退。
- 机械臂动作不再因通信耗时和调度抖动产生追赶跳变。
- 启动等待缩短到约 1.5 秒，10 帧预热本身仅约 0.36～0.43 秒。
- 性能和故障日志分层，既能长期观察，又不会逐帧刷屏。

### 7.2 已知代价和风险

- ReLU 的测试集 Recall 降低 0.01130、mAP50-95 降低 0.01023，需要继续统计
  不同光照、远距离和画面边缘的实际漏检率。
- UVC 在机械臂动作前后切换约增加 1.3 秒总时间，但动作期间无需视觉，且换来 USB
  稳定性。
- 正式流程仍是串行处理。同步取帧稳定，但无法让采集与推理跨 CPU 流水执行。
- StarryOS 默认 NPU core 0 是当前实测最优选择，不代表多核 NPU 已被充分利用。
- 初始化顺序只规避 UVC 与 ext4/SDHCI 并发慢读，没有修复底层 I/O 问题。

### 7.3 为什么 StarryOS 当前仍然较慢

经过模型、UVC 和日志优化后，StarryOS 的 UVC-only 能够取得约 27.6～28.6 FPS，
但这只代表摄像头链路单独运行时的能力。最新对比分为两层：

- 去除底盘和机械臂的视觉基准：Linux 30.01 FPS，StarryOS 16.01 FPS；
- 正式流程稳态：Linux 30.00 FPS，StarryOS 约 16.05 FPS。

正式流程稳态与去除底盘/机械臂的视觉基准基本一致，Linux 也基本不变。当前差距仍由
以下几层原因共同造成，不能简化为某一个固定的 NPU 耗时。

#### 7.3.1 NPU 忙轮询是重要因素，但不是唯一根因

当前 StarryOS 的 RK3588 NPU 提交路径在任务执行期间持续读取 NPU 完成状态：

```text
当前实现：提交 NPU 任务 → CPU 循环查询完成状态 → NPU 完成 → 退出循环
理想实现：提交 NPU 任务 → 当前线程睡眠 → NPU 中断 → 唤醒等待线程
```

当前循环没有进展时只执行 `spin_loop()`，NPU 中断处理也没有形成“中断到达后唤醒
等待任务”的完整机制。CPU 因此会在 NPU 工作期间持续忙等，并挤压 libusb 事件、
UVC 完整帧交付及其他用户线程的调度机会。

摄像头此时可能已经产生并开始传输下一帧，但数据还需要经过 USB 完成事件、libusb
接收和 libuvc 组装，才能成为主线程可取得的完整图片。Linux 能在主线程处理当前帧时
同步推进这条后台链路；StarryOS 中 NPU 和 RKNN 线程挤压其调度机会，主线程进入
`uvc_stream_get_frame()` 阻塞后，USB 链路才继续追赶。因此 StarryOS 稳态取帧等待
约 29.1 ms，而 Linux 约 15.8 ms。这不是“主线程不结束，USB 完全不能运行”，而是
USB 后台处理不够及时，无法在主线程处理期间准备好下一张完整图片。

隔离测试已经证明这种影响：StarryOS 仅运行 UVC 时接近 28～30 FPS，同时连续运行
NPU 后摄像头交付可降到 11.73 FPS；诊断程序在每次推理后主动让出一次调度机会，
摄像头又恢复到 29.66 FPS。因此 NPU 忙轮询确实会挤压 USB 完成链。

一次无板端写日志的完整流程中，找桶阶段 `rknn_run=0` 时为 8.72 FPS，JPEG 解码
35.51 ms，仍存在较大的未分类等待。该阶段目前只有一个有效样本，不能作为稳定均值，
但足以说明 NPU 忙轮询不足以解释全部性能差距；重复解码和系统调度仍需独立复测。

#### 7.3.2 直接的用户态上限：正式流程仍然串行

当前主业务线程按顺序执行：

```text
取帧
→ JPEG 解码
→ NPU 输入、推理和输出
→ 检测后处理
→ 车轮/舵机控制
→ 再取下一帧
```

主线程进行 JPEG 解码、NPU 推理和控制时，不会同时处理下一帧。摄像头虽然仍可在
后台产生约 30 FPS，但中间旧帧会被跳过，直到主线程完成本轮后才取得最新完整帧。

最新串口前台稳态追球窗口的代表值为：

| 阶段 | Linux | StarryOS |
| --- | ---: | ---: |
| 取帧等待 | 约 15.8 ms | 约 29.1 ms |
| JPEG 解码 | 约 4.8 ms | 约 8.9 ms |
| `rknn_run` | 约 12.0 ms | 约 15.7 ms |
| 控制 | 约 0.12 ms | 约 2.4 ms |
| 总帧时间 | 约 33.3 ms | 约 62.3 ms |

串行结构是用户态的直接上限：StarryOS 每帧约 29 ms 取帧等待、9 ms JPEG 解码和
16 ms NPU 运行会顺序累加，稳态处理能力约为 16 FPS。

同步 UVC 已经修复“摄像头链只能向程序交付约 11 FPS”的旧回调问题，但没有把取帧、
解码、推理和控制改成流水线，也没有消除完整负载下的调度停顿。

#### 7.3.3 多核没有自动解决问题：线程调度和亲和性仍不完善

StarryOS 即使以 SMP=8 启动，也只表示系统有 8 个 CPU 可用，不表示相关任务已经
自动、稳定地分配到不同 CPU。完整程序同时涉及：

- 主业务线程；
- libusb 事件线程；
- RKNN 运行时内部线程；
- NPU 驱动忙轮询路径；
- 网络、中断和其他内核任务。

当前新建的 libusb 和 RKNN 线程不一定完整继承调用者设置的 CPU mask，用户态也不能
可靠地按线程 ID 重新绑定这些内部线程。即使把外层采集和推理线程指定到不同 CPU，
内部辅助线程和内核忙轮询仍可能相互干扰。

因此当前“多核可用”不等于“摄像头、NPU 和控制已经并行”。在亲和性和 NPU 中断等待
机制完善前，直接增加采集线程或启用 NPU 三核并不能保证提升；正式程序实测
core 0/1/2 只有 12.92～13.21 FPS，未优于稳定的 core 0。

综合来看：**串行用户态流程限制可利用的并行度；NPU 忙轮询会挤压 USB 调度；完整
控制负载下还存在更大的未归入阶段停顿。线程调度和亲和性不完善使 8 核环境无法自动
缓解这些问题。当前证据不支持把全部差距归因于 NPU。**

### 7.4 下一步优先级

1. **补齐完整流程计时**：为 Feetech 通信、找桶二次解码、主循环未埋点区间和
   UVC 暂停/恢复增加独立墙钟统计，避免继续根据单一组件猜测。
2. **桶检测重复解码**：当前找桶不运行 NPU 的一个有效样本只有 8.72 FPS，应先
   复用同一帧解码结果并做三次 A/B；无稳定收益则撤销。
3. **StarryOS NPU 完成机制**：当前 RK3588 NPU 提交路径轮询完成状态，空转时
   使用 `spin_loop()`，中断处理函数没有完成唤醒。应实现中断 + 等待队列，避免
   RKNN 忙等挤压 USB 完成任务。
4. **线程亲和性**：修复新线程继承 CPU mask 和按 TID 设置亲和性的能力，再验证
   libusb 事件线程、采集线程和 RKNN 辅助线程分核是否有效。
5. **可控的双缓冲流水线**：仅在上述调度能力可靠后，重新实现“采集线程只保留
   最新帧，处理线程解码/推理/控制”。必须验证控制延迟、退出和 UVC 暂停恢复，
   不能只看平均 FPS。
6. **ReLU 长期准确率**：统计多场景夹球成功率和漏检率，以数据决定是否继续训练，
   不只看一次闭环。
7. **UVC + ext4/SDHCI 并发**：在 StarryOS 内核定位吞吐退化；用户态启动顺序可作为
   稳定规避保留。

`capture_wait` 的详细根因和隔离矩阵见
[StarryOS capture_wait 定位](./p4-capture-wait-root-cause.md)。
