当前建议围绕“先准确测量，再做低风险优化，最后切换640×480模型”展开。摄像头继续保持 `640×480 MJPEG @ 30 FPS`，不改变现有控制视野。

> P2 已完成并通过 Linux/StarryOS 实机 A/B，结果见
> [P2 640×480 模型测试结果](./p2-640x480-model-result.md)。

## P0：性能统计与日志优化

这是后续判断优化效果的基础，应先完成。

### 1. 增加10秒性能窗口

统计：

```text
camera_fps       用户态程序实际取得的完整帧率
effective_fps    完成检测和控制的有效帧率
busy_fps         排除摄像头等待后的纯处理能力
captured         摄像头收到的帧数
processed        实际处理的帧数
```

分阶段统计：

```text
capture_wait
jpeg_header
jpeg_decode
letterbox_copy
rknn_input
rknn_run
rknn_output
postprocess
control
total
```

每10秒输出：

```text
平均值、P50、P95、最大值
```

使用 `CLOCK_MONOTONIC`，摄像头和NPU预热完成后再开始统计。

### 2. 降低连续状态日志频率

当前球位置、轮速等每帧打印，建议改为：

- 连续状态默认每1秒打印一次；
- 状态即使来回切换，也必须等到时间间隔到达后再打印；
- 错误、超时、重试立即打印；
- 性能统计每10秒打印一次；
- 提供调试开关恢复逐帧输出。

建议环境变量：

```bash
AKA_STATE_LOG_INTERVAL_MS=1000
```

设为0时恢复逐帧日志。

### 3. 精简机械臂日志

当前同一步骤会重复打印多次，应改成只打印：

```text
步骤开始
步骤完成
步骤超时
动作失败
整套动作完成
```

### 4. 删除打印周围多余的dup2

很多 `printf(stdout)` 前后仍切换 `stderr`，每帧产生额外系统调用。普通状态日志直接写 `stdout`，RKNN噪声继续单独抑制即可。

## P1：不改变模型的低风险运行时优化

这些优化不改变识别结果和控制坐标，可先在当前 `640×640` 模型上验证。

### 1. 复用TurboJPEG解码器

当前每帧执行：

```text
tjInitDecompress
tjDestroy
```

应在程序启动时创建一次，退出时销毁。

### 2. 复用RGB临时缓冲区

当前每帧都有：

```text
malloc
free
```

改为初始化时分配最大缓冲区，后续重复使用。

### 3. 减少letterbox复制

当前流程：

```text
JPEG → 临时640×480 RGB → 复制到640×640中间
```

可直接将JPEG解码到目标缓冲区的中间区域，保留上下灰边但取消中间RGB复制。

切换到 `640×480` 模型后，可直接解码到模型输入缓冲区。

### 4. 修复桶检测的重复解码

当前找桶状态中，同一帧先解码成 `640×640`，随后又解码成 `640×480` 做HSV桶检测。

应先判断游戏状态：

```text
追球状态：只解码模型输入并运行RKNN
找桶状态：只解码640×480并运行HSV
机械臂动作状态：按需要暂停或跳过视觉
```

找桶阶段不再执行无用的模型输入解码。

## P2：将模型输入改为640×480

这是主要性能优化方向。

目标模型输入：

```text
训练/ONNX：NCHW [1,3,480,640]
RKNN运行：NHWC [1,480,640,3]
```

理论变化：

```text
输入像素：409600 → 307200，减少25%
YOLO候选位置：8400 → 约6300，减少25%
RKNN输入数据：1.2 MiB → 0.9 MiB
上下补边：取消
```

### tennis-train需要修改

1. `--imgsz` 支持矩形尺寸，而不是只能接受单个整数。
2. 训练、验证、导出统一使用 `480×640`。
3. 校准图片不能继续硬编码：

```python
resize((640, 640))
```

4. 校准预处理必须和实际部署一致，保持宽高比，不能随意拉伸。
5. 增加或明确RKNN转换流程。目前仓库主要记录ONNX/CVI模型流程，缺少完整可复现的RK3588 RKNN生成步骤。
6. 先用现有权重导出 `640×480` 模型做A/B测试；如果准确率下降，再进行矩形输入微调或重新训练。

### aka-rk3588需要适配

当前大部分代码已经从RKNN模型动态读取宽高，因此基础结构可以复用，但需要确认：

- RGB缓冲区按模型实际尺寸分配；
- `decode_mjpeg()`在 `640×480 → 640×480` 时直接解码；
- `pad_x=0`、`pad_y=0`、`scale=1`；
- 后处理候选数量从模型张量动态读取，不能写死8400；
- 输出框仍映射到摄像头 `640×480` 坐标；
- LeKiwi控制器继续使用 `640×480`；
- 停车尺寸和中心容差理论上不需要按比例修改，但必须实机复核。

## P3：后续可选优化

这些不建议与第一轮修改一起做：

- 直接解析INT8输出，取消 `want_float=1` 的FP32转换；
- RKNN零拷贝输入；
- RGA硬件颜色转换或缩放；
- 多线程解码和推理流水线；
- 异步日志线程；
- 调整摄像头分辨率或格式。

这些修改复杂度更高，应在10秒性能统计明确瓶颈后再决定。

## 验证方案

当前 `640×640` 和新 `640×480` 模型需要使用相同场景对比：

1. Linux和StarryOS分别运行。
2. 每种方案至少统计6个10秒窗口。
3. 对比：

```text
effective_fps
rknn_run平均值与P95
JPEG解码时间
输出处理时间
帧耗时P95和最大值
检测置信度
球框中心和尺寸抖动
停车位置
抓球成功率
```

4. 确认找球、靠近、停车、夹球、找桶、放球完整流程没有回归。

建议实施顺序：

```text
P0 性能统计和日志限流
→ 当前模型建立基线
→ P1 低风险解码优化
→ 再次测量
→ P2 导出并接入640×480模型
→ Linux/Starry A/B测试
```

以上是建议纳入本轮的完整优化范围，暂不包含P3的高复杂度优化。
