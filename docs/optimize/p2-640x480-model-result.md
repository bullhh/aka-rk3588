# P2 640×480 模型测试结果

## 结论

2026-07-28 已将默认检测模型从 `640×640` 改为与摄像头一致的
`640×480`。模型权重保持不变，只调整静态输入、YOLO 网格和 RKNN
量化；INT8 校准只使用 Roboflow 官方验证集。

新模型在 Linux 和 StarryOS 均能加载并识别实机画面中的网球。固定输入
NPU 测试和 StarryOS 实机完整闭环均表明，这项修改有明确性能收益，已
部署为板端默认 `models/tennis.rknn`。

| 系统 | 旧模型 640×640 | 新模型 640×480 | 推理耗时降低 |
| --- | ---: | ---: | ---: |
| Linux，100 次平均 | 42.05 ms | 16.22 ms | 61.4% |
| StarryOS Warn，100 次平均 | 93.98 ms | 19.84 ms | 78.9% |

> 上表是相同测试程序的 RKNN-only 固定输入数据，不包含摄像头、JPEG
> 解码、后处理和控制时间。

## StarryOS 完整闭环复测

2026-07-28 在 `Warn` 日志、8 核 StarryOS 环境下进行了一次真实闭环：

```text
找球 -> 停车 -> 夹球 -> 找桶并对齐 -> 放球 -> 返回找球
```

默认模型 SHA-256 为
`23ad72a031160ab712cede1a9fc28c38813aebae020cc66b224f03e06f2d4d69`，
运行时确认输入为 `640×480`、预热 10 帧。夹球第一次尝试成功，软件检测
`gripper_hold=yes`；随后放球流程完成，无机械臂控制器、Feetech 通信或
超时错误。

下表选择放球完成后的 10.03 秒纯视觉稳态窗口，与旧 640×640 模型的
StarryOS Warn 稳态基线比较。机械臂动作期间会主动暂停摄像头，跨动作
窗口不参与性能比较。

| 指标 | 旧模型基线 | 新模型本次稳态 | 变化 |
| --- | ---: | ---: | ---: |
| 摄像头帧率 | 7.83 FPS | 8.28 FPS | +5.7% |
| 有效处理帧率 | 6.32 FPS | 8.38 FPS | +32.6% |
| 单帧平均耗时 | 157.79 ms | 119.36 ms | -24.4% |
| 单帧 P50 | 约 134.4 ms | 42.09 ms | 明显降低 |
| JPEG 解码 | 8.30 ms | 8.34 ms | 基本不变 |
| RKNN 推理 | 88.24 ms | 22.71 ms | -74.3% |

本次完整流程的 RKNN 耗时与 RKNN-only 的 19.84 ms 接近，说明
`640×480` 模型的推理收益在真实流程中能够保留。有效帧率已经接近摄像头
实际供帧率，当前 StarryOS 整体帧率上限主要是 UVC 约 8 FPS，而不再是
NPU 推理。当前结论只来自一个无机械臂动作的 10 秒稳态窗口；如需做严格
长期基准，应按 P0 约定采集至少 6 个稳态窗口。

## 数据集与精度检查

Roboflow 数据集共 12,237 张：train 11,268、valid 684、test 285。当前
部署模型在官方 test 集上的 640×640 PyTorch 基线为：

```text
Precision 0.935
Recall    0.903
mAP50     0.922
mAP50-95  0.723
```

曾从原 ONNX 恢复可训练权重，并在完整 train 集进行一轮低学习率、480
尺度矩形微调。独立 test 结果下降，因此没有采用微调权重：

| 模型与评估尺度 | mAP50 | mAP50-95 |
| --- | ---: | ---: |
| 原权重，480 | 0.904 | 0.715 |
| 微调权重，480 | 0.893 | 0.695 |
| 微调权重，640 | 0.895 | 0.699 |

最终方案保留原权重。新 RKNN 使用全部 684 张官方 valid 图片校准；在
test 集前 50 张上对比量化前 FP32 输出：

```text
最高置信度平均绝对误差  0.0079
最高框平均 IoU           0.876
全部置信度平均相关系数   0.99949
FP32 阳性保留            50 / 50
```

StarryOS 实机相邻两次单帧检测结果也一致：新模型置信度 0.963、框
约 136×136；旧模型置信度 0.954、框约 139×133。

## 生成方法

在 `tennis-train` 仓库执行：

```bash
python scripts/reshape_yolov8_onnx.py \
  --input rknn/best_opset19.onnx \
  --output runs/deploy/tennis-640x480.onnx \
  --width 640 --height 480

python scripts/convert_rknn.py \
  --onnx runs/deploy/tennis-640x480.onnx \
  --output runs/deploy/tennis-640x480-official.rknn \
  --calibration-dir dataset/valid/images \
  --calibration-count 684 --seed 42
```

转换使用 RKNN Toolkit2 2.3.2、`rk3588` 目标和单核稳定模型。生成脚本会
把 `[1,5,6300]` 输出拆为 `boxes_raw` 与 `scores_raw`，与 aka-rk3588
现有后处理接口匹配。

## 验证边界

已完成 Linux、StarryOS 的模型加载、单帧识别、量化输出一致性和
RKNN-only 性能 A/B，并完成一次机械臂和车轮真实闭环。控制坐标仍为
原生 640×480，本次没有因模型尺寸变化而调整停车、夹球或放桶参数。
板端旧模型保存在 `models/tennis-640x640-before-640x480.rknn`。

一次闭环只能确认基本功能和本次场景有效，不能代表不同光照、球位和桶位
下的长期成功率；夹球准确率仍需通过多次重复实机测试统计。
