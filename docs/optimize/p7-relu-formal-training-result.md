# ReLU 模型正式训练与实机测试

## 结论

使用完整 Roboflow 数据集重新训练后，ReLU 模型已经具备可用检测精度，并在
RK3588 的 Linux 和 StarryOS 上稳定减少约 24% 的 NPU 推理时间。模型已通过实际
捡球、找桶和放球闭环，并替换为默认模型：

```text
models/tennis.rknn
SHA256: 2eee3c422fb9f7fdeea5b9db5df047ac4f6d9b8047f9b654f75c3cb012db0081
```

机器人文件系统保留原 SiLU 模型备份
`models/tennis-silu-640x480-backup.rknn`，SHA256 为
`23ad72a031160ab712cede1a9fc28c38813aebae020cc66b224f03e06f2d4d69`。

## 训练方法

- 数据集：项目使用的完整 Roboflow 网球数据集。
- 数量：训练集 11268 张、验证集 684 张、测试集 285 张。
- 初始权重：当前 SiLU 基线模型对应的 `best.pt`。
- 训练和验证使用 `imgsz=640`；导出部署模型时固定为 640x480。网络内部 56 个
  Conv 激活由 SiLU 替换为 ReLU。
- 优化器：AdamW，初始学习率 0.0005，全局 batch 32。
- 训练方式：CPU 双进程 DDP，使用完整数据集和原有数据增强。
- 计划上限 50 epoch；训练到第 5 epoch 时验证指标已经平台化并开始回落，因此停止，
  使用 Ultralytics 保存的 `best.pt`，避免继续训练造成过拟合和无效计算。

训练脚本位于 `tennis-train/scripts/train_relu_yolov8.py`。脚本在训练真正开始后检查
`ReLU=56、SiLU=0`，防止 Ultralytics 重建网络时悄悄恢复为 SiLU。

## 精度结果

以下结果均使用相同数据、图像尺寸和评估参数：

| 模型 | 数据集 | Precision | Recall | mAP50 | mAP50-95 |
| --- | --- | ---: | ---: | ---: | ---: |
| 原 SiLU | validation | 0.93460 | 0.85601 | 0.87426 | 0.74273 |
| ReLU best | validation | 0.95127 | 0.82993 | 0.85770 | 0.72074 |
| 原 SiLU | test | 0.93495 | 0.90303 | 0.92238 | 0.72285 |
| ReLU best | test | 0.94193 | 0.89173 | 0.92463 | 0.71262 |

独立测试集上，ReLU 的 mAP50 提高 0.00225，Recall 降低 0.01130，mAP50-95 降低
0.01023。它不是无损替换，但已经与原模型处于同一可用精度区间。

## 导出和 INT8 量化检查

导出的 ONNX 输入为 `[1, 3, 480, 640]`、输出为 `[1, 5, 6300]`，图中包含 56 个
ReLU，不再包含内部 SiLU。RKNN 使用全部 684 张验证图片做 INT8 校准。

从测试集取前 50 张图片对比 ONNX FP32 与 RKNN INT8 输出：

- 最高置信度平均绝对误差：0.00508；
- 最高分检测框平均 IoU：0.89819；
- 全部置信度相关系数：0.99944；
- FP32 的 50 个阳性样本在 INT8 中保留 50/50。

候选 RKNN 大小为 3,588,424 字节，原模型为 4,107,848 字节，减少 12.64%。

## RK3588 固定输入 A/B 测试

两个模型均固定使用 NPU core 0，预热 5 次后连续执行 100 次；输入、输出获取方式和
测试程序完全相同，因此结果不受摄像头帧率、场景变化和机器人控制影响。

| 系统 | 模型 | 平均 NPU 时间 | 理论纯推理 FPS | 改善 |
| --- | --- | ---: | ---: | ---: |
| Linux | 原 SiLU | 15.83 ms | 63.18 | - |
| Linux | 正式 ReLU | 11.98 ms | 83.45 | 24.30% |
| StarryOS | 原 SiLU | 18.04 ms | 55.43 | - |
| StarryOS | 正式 ReLU | 13.79 ms | 72.50 | 23.55% |

这里的 FPS 是只计算 RKNN 推理的理论值，不是完整程序的真实处理帧率。完整程序还包括
UVC 等待、JPEG 解码、输入复制、后处理和控制逻辑，最终帧率不会按相同比例提高。

## 真实链路安全测试

Linux 和 StarryOS 均完成以下检查：

1. UVC 以 640x480@30fps 打开；
2. RKNN 正确加载 640x480、6300 个候选框的 ReLU 模型；
3. 实际画面中的网球被识别；
4. 控制状态进入 `BALL_FINE_LEFT`；
5. 使用 `LEKIWI_STOP_AFTER_CHASE=1`，连续 3 帧确认后停车退出，没有进入夹球动作。

Linux 输出：

```text
[STATE] LEKIWI_CHASE label=BALL_FINE_LEFT area=0.090 off=-71 size=171 L=-8 R=8 ready=0
[SAFETY] STOP_AFTER_CHASE confirmed=3 label=BALL_FINE_LEFT L=-8 R=8 ready=0
```

StarryOS 得到相同的状态和安全退出结果。这证明候选模型不仅能单独运行，也能接入现有
摄像头、检测、追球控制链路。

## StarryOS 正式程序 A/B

两个模型均使用正式 `tennis ... lekiwi` 程序、NPU core 0、相同场景和 10 秒统计窗口。
排除包含模型初始化的第一个窗口后：

| 模型 | 稳定 effective FPS | 平均 effective FPS | 平均 RKNN run |
| --- | --- | ---: | ---: |
| 原 SiLU | 13.39、13.66、13.89 | 13.65 | 35.12 ms |
| 正式 ReLU | 14.29、13.90、14.13 | 14.11 | 26.41 ms |

同场景下完整链路平均帧率提高约 3.4%，NPU 阶段降低约 24.8%。最终帧率提升小于纯 NPU
提升，是因为完整流程还受约 15fps 的摄像头供帧、JPEG 解码和控制阶段限制。

## 实际闭环结果

机器人放回地面后，ReLU 模型完成了一次未注入假检测、未放宽配置的实际闭环：

1. 从 `BALL_FORWARD` 接近小球并进入 `PICK_BALL`；
2. 完成 11 步夹球轨迹，夹爪位置 47.4 度，`gripper_hold=yes`；
3. 夹取后画面中不再有球，判定 `holding=yes`；
4. 进入 `FIND_BUCKET`，完成桶的搜索、左右对齐和距离接近；
5. 完成 6 步安全放球轨迹；
6. 输出 `PUT_BALL done -> CHASE_BALL`，回到下一轮追球。

闭环后的正常视觉窗口达到 `camera=16.30fps、effective=15.30fps、rknn_run=19.74ms`。
机械臂动作期间的窗口会包含十几秒的阻塞轨迹，不能用于衡量视觉帧率。

原 SiLU 模型随后也进行了地面测试，但球已因上一轮放球改变位置，连续两次夹取后仍在
画面中，因此不能将该次夹取失败作为两个模型的准确率对比。替换依据是同场景 A/B、
固定输入测试以及 ReLU 完整闭环共同成立，而不是这次非同条件的夹球结果。

## 后续验证建议

当前 ReLU 已设为默认模型。后续继续观察多距离、左右边缘、不同光照和球桶同时出现时
的成功率；若发现远距离小球或边缘定位明显退化，可立即恢复板端 SiLU 备份，再补充相应
样本微调。
