# StarryOS 推理后等待时间测试

## 结论

当前正式程序采用串行流程：

```text
取帧 → 解码 → NPU推理 → 控制 → 取下一帧
```

在这个结构下，最大帧率对应的等待时间是 **0 微秒**，即不增加额外休眠。
`usleep(1)` 的长时间结果与不休眠完全相同，不能有效降低串行取帧等待；更大的
请求值反而会触发 StarryOS 较粗的实际休眠粒度并明显降低帧率。

只有将摄像头消费与 NPU 推理改成两个并发线程后，推理线程使用 `usleep(1)` 才能
让摄像头从 11.73 FPS 恢复到 29.66 FPS。因此 `1 微秒` 是未来并行流水线的候选值，
不是当前串行程序应加入的优化。

## 串行实测

测试内容为“同步取一帧，然后执行一次完整 `detect_run()`”，使用同一摄像头和
`640×480` RKNN 模型。0 和 1 微秒均进行了 30 秒初测及 60 秒复测。

> 本页使用的是固定 RGB 输入的诊断循环和三核 NPU，不包含正式程序的 JPEG 解码与
> 车轮控制，因此 18 FPS 不能作为正式程序帧率。正式 `run_lekiwi_full.sh` 的复测与
> 最终结论见 `p6-starry-formal-program-test.md`。

| 请求等待时间 | 有效帧率 | 说明 |
| ---: | ---: | --- |
| 0 µs，30 秒 | 18.62 FPS | 基准 |
| 0 µs，60 秒 | 18.40 FPS | 基准复测 |
| 1 µs，30 秒 | 18.85 FPS | 与基准差异很小 |
| 1 µs，60 秒 | 18.41 FPS | 与基准相同 |
| 2 µs | 18.32 FPS | 无提升 |
| 3 µs | 18.13 FPS | 开始下降 |
| 5 µs | 13.52 FPS | 触发较大的实际休眠档位 |
| 10 µs | 13.70 FPS | 明显下降 |
| 100 µs | 13.50 FPS | 明显下降 |

将两轮数据按总帧数和时间合并后：

```text
0 µs: 18.47 FPS
1 µs: 18.56 FPS
```

差值只有 0.09 FPS（约 0.5%），小于不同窗口自身的波动，不能视为性能提升。

## 为什么与并发测试不同

并发测试中，摄像头线程始终调用 `getFrame()`，NPU 在线程中连续推理。NPU 线程
若完全不阻塞，会持续挤占 StarryOS 的 USB 完成处理；一次 `usleep(1)` 可以产生
有效调度点，因此摄像头可恢复接近 30 FPS。

串行测试每次推理结束后本来就会进入阻塞式 `getFrame()`。再额外休眠一次不会增加
处理并行度，也没有让下一帧更早完成，只会增加串行周期。StarryOS 当前对几微秒
休眠的处理还存在明显阶跃：请求达到约 5 微秒后，实际每帧增加约 20 毫秒，因此
帧率从约 18.4 FPS 下降到约 13.5 FPS。

## 决策

- 当前正式捡球程序：不增加推理后休眠，等待时间保持 `0`。
- 不保留本轮临时诊断代码。
- 若后续实现独立采集线程和最新帧队列，再使用 `1 微秒` 作为并行版本起始值，重新
  测量摄像头帧率、有效处理帧率及控制延迟。
