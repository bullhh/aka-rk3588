# 用户态程序运行与控制原理

`build/tennis` 是三足捡球机器人的用户态控制核心。它在一个持续运行的任务状态机中
完成图像获取、网球识别、三轮底盘控制、机械臂抓取、桶检测和放球，而不是分别运行
几个互不相关的演示程序。

本文沿着“一张摄像头图像如何变成机器人动作”的路径，介绍目前使用的取帧方法、视觉
处理流程、底盘闭环、机械臂轨迹和完整任务状态机。

## 1. 从图像到动作的完整链路

```text
UVC 摄像头持续输出 640×480 MJPEG（请求 30 FPS）
  ↓
USB 控制器、libusb 和 libuvc 接收数据
  ↓
主循环取得下一张可用的完整 MJPEG 图像
  ↓
libjpeg-turbo 解码为 640×480 RGB
  ↓
RKNN Runtime 将 RGB 输入 RK3588 NPU
  ↓
YOLOv8 输出候选框，后处理得到网球位置
  ↓
根据任务状态选择追球控制或桶检测
  ↓
生成三轮底盘速度，或者推进机械臂动作步骤
```

各层代码位置如下：

| 处理环节 | 主要代码 |
| --- | --- |
| UVC 图像获取 | `capture/uvc_capture.cpp` |
| JPEG 解码、循环和任务状态机 | `tennis.cpp` |
| RKNN 推理及 YOLO 后处理 | `detect/detect.cpp`、`3rd/yolov8_src/` |
| 球和桶的接近控制 | `robot/lekiwi_task_controller.cpp` |
| 三轮运动学和舵机速度写入 | `robot/omni_base.cpp` |
| 机械臂反馈、轨迹和任务步骤 | `robot/feetech_arm.cpp`、`robot/lekiwi_task_controller.cpp` |
| Feetech 通信 | `feetech/feetech_bus.cpp` |

程序先初始化 Feetech 底盘和机械臂，再加载 RKNN 模型，最后打开摄像头。先完成 NPU
内存分配可以避免模型初始化与 UVC 数据流同时争用内存和调度资源。摄像头开始工作后，
程序跳过前 10 帧，让曝光和图像数据稳定，然后进入任务循环。

## 2. 摄像头图像如何交给主循环

### 2.1 摄像头和 USB 持续工作

程序通过 `uvc_get_stream_ctrl_format_size()` 请求 `640×480 MJPEG @ 30 FPS`，然后建立
UVC stream。摄像头不会等主循环调用后才拍照；只要 stream 处于运行状态，摄像头、
USB 控制器和 libusb 就会持续传输和接收数据。

主循环调用 `uvc_stream_get_frame()` 取得一张已经完整接收的图像。如果下一张完整图像
尚未就绪，该调用会等待；等待期间主线程不会空转占满 CPU。图像到达后，程序立即将
MJPEG 数据复制到自己的缓冲区，随后开始解码和推理。

```text
后台：摄像头曝光 → USB 分包传输 → libusb/libuvc 组装完整图像
前台：取得完整图像 → JPEG 解码 → NPU 推理 → 控制 → 再取得图像
```

### 2.2 使用最新可用图像，避免旧帧积压

机器人关心的是目标现在的位置，而不是几百毫秒前的位置。因此程序不会维护一个等待
逐张处理的长图像队列。当主循环完成上一帧处理后，它取得此时可以交付的最新完整图像，
较旧且没有被处理的图像不再进入控制链路。

假设摄像头每 33 ms 产生一帧，而一轮处理用了 70 ms：

```text
 0 ms：第1帧到达，主循环取得它并开始处理
33 ms：摄像头产生第2帧，主循环仍在处理第1帧
66 ms：摄像头产生第3帧
70 ms：主循环结束本轮，取得此时可用的最新完整图像
```

这种方法限制了控制所使用图像的年龄，避免图像越积越多、机器人一直依据旧位置移动。

性能日志中的三个帧率含义不同：

| 指标 | 含义 |
| --- | --- |
| `camera` | 主循环成功取得完整图像的速率，不是摄像头曝光频率 |
| `effective` | 完成取帧、解码、推理和控制的真实处理帧率 |
| `busy` | 扣除等待图像时间后的理论处理能力 |

完整程序的实际处理速度应以 `effective` 为准。

### 2.3 单帧处理为何仍按顺序执行

每轮主循环按以下顺序工作：

1. 等待并复制一张 MJPEG 图像；
2. 读取 JPEG 信息并用 libjpeg-turbo 解码；
3. 将 640×480 RGB 数据设置为 RKNN 输入；
4. 调用 `rknn_run()` 并等待 NPU 完成；
5. 取得模型输出并执行置信度过滤、非极大值抑制和坐标还原；
6. 根据状态机计算底盘命令或进入机械臂任务；
7. 记录本轮阶段耗时，然后开始下一轮。

应用没有建立独立的图像生产队列和推理队列。这样每个检测结果天然对应本轮控制，避免
帧序号、任务状态和电机命令错配。多核操作系统仍可同时运行 USB 事件、中断处理和其他
后台任务，但不会自动把应用中的 JPEG 解码、NPU 提交和控制计算拆到不同 CPU。

## 3. 网球检测与目标选择

### 3.1 640×480 RKNN 模型

摄像头和模型都使用 640×480。程序把 RGB 图像交给 RKNN Runtime，NPU 输出候选框和类别置信度。后处理过滤低置信度
候选框，执行非极大值抑制，最后把坐标映射回 640×480 摄像头画面。

### 3.2 多个网球中的选择

画面中可能同时出现多个网球。移动控制器综合候选框面积和候选框到目标中心的横向距离
评分：面积较大、靠近抓取中心的球优先。这样既倾向于选择更近的球，也减少机器人在
相邻目标之间频繁切换。

如果暂时看不到球，程序记录最后一次看到球的左右方向，并向该方向旋转搜索；从未看到
过球时保持停止。重新发现球后恢复正常接近控制。

## 4. 三轮底盘如何追踪目标

### 4.1 从目标框得到距离和方向

对于网球，程序使用检测框宽、高中的较大值作为距离量 `size`；球越近，`size` 越大。
对于桶，使用 `sqrt(width × height)` 作为等效尺寸，降低检测框宽高比例变化造成的抖动。
目标中心与画面目标中心之差形成横向误差 `off`。

这两个量分别回答：

- `size` 是否达到停车距离；
- `off` 是否已经左右对正。

只有距离和中心连续满足配置要求，程序才会把 `ready` 置为 1 并切换到下一任务。

### 4.2 三轮运动学

状态控制器先生成抽象的左右速度，再由 `OmniDriveAdapter` 转换为三轮底盘运动。底层
`OmniBase::drive_body(x, y, theta)` 根据三个轮子在底盘上的安装角计算各轮角速度：

```text
wheel_i = cos(angle_i) × x
        + sin(angle_i) × y
        + base_radius × theta
```

三个轮子的安装方向分别对应左轮、后轮和右轮。计算结果若超过舵机允许值，会按相同比例
整体缩小，保持运动方向不变。最终使用一次 Feetech 批量写命令更新 ID7、ID8、ID9，
避免三个轮子因逐个写入产生明显时间差。

追球和找桶状态主要使用车体前后速度 `x` 与旋转速度 `theta`：左右抽象速度的平均值
换算为前进/后退速度，两者之差换算为旋转速度。`OmniBase` 同时支持横移速度 `y`，
供 `test-base left/right` 等三轮底盘单项测试使用。

初始化轮子时，程序先关闭扭矩、切换速度模式、设置目标速度为 0，再重新开启扭矩，
防止速度模式中残留的非零目标导致上电突然转动。

### 4.3 远距离转向与近距离对正

目标位于允许区域之外时，小车先原地旋转，使目标进入抓取区域。目标进入区域后开始
前进；若仍存在中等横向偏差，则使用左右轮差形成弧线，一边接近一边修正，而不是每次
偏离都停下原地旋转。

精调状态使用两个不同阈值：误差超过较大的进入阈值才开始精调，误差小于较小的退出
阈值才结束精调。这种滞回设计避免检测框在边界附近波动时反复切换“直行—转向”。
已经到达停车距离但仍未对正时，程序才原地低速微调。

### 4.4 连续减速和预测制动

程序对 `size` 做平滑滤波，并根据相邻帧的变化计算接近速度。然后按照配置的预测时间
估算未来目标尺寸：

```text
predicted_size = filtered_size + max(size_rate, 0) × lookahead_time
```

距离较远时使用远速；进入减速区后，在远速和近速之间连续插值。即使当前 `size` 尚未
到达目标，如果 `predicted_size` 已经达到停车值，程序也会提前输出 `BALL_BRAKE` 或
`BUCKET_BRAKE`。制动结束后重新观察目标：太远则低速前进，太近则低速后退。

最后还需要连续 `ball_stable_frames` 或 `bucket_stable_frames` 帧同时满足距离和中心
条件。预测制动负责降低惯性过冲，稳定帧负责过滤单帧误检，两者作用不同。

## 5. 抓球任务如何执行

### 5.1 从配置姿态得到实际抓取点

`grab_id1_deg～grab_id5_deg` 定义夹球瞬间的基础关节姿态。程序使用肩部和肘部的正向
运动学得到基础前后、高度位置，再叠加：

- `grab_forward_offset_cm`：前后修正；
- `grab_lateral_offset_cm`：左右修正，并换算为 ID1 水平角度；
- `grab_height_offset_cm`：高度修正；
- `grab_pitch_offset_deg`：最终腕部俯仰修正。

随后逆运动学计算肩部和肘部目标。最终抓取姿态严格使用配置的 ID4 角度，不施加额外的
“总俯仰角”约束；预抓取姿态只为安全接近自动计算舒适的腕部角度。

### 5.2 抓球动作序列

```text
保持 ID1 当前方向，收回 ID2～ID4
并在收回过程中打开夹爪、对齐 ID5
→ ID1 转向抓取方向
→ PRE_GRAB：到球上方的安全点
→ GRAB：沿接近方向下降到最终姿态
→ 等待机械结构稳定
→ ID6 闭合夹爪
→ 判断夹爪接触
→ CLEAR：沿原路径抬离地面
→ CARRY：平滑收臂到行驶姿态
```

任务开始前会检查 HOME 到 PRE_GRAB、PRE_GRAB 到 GRAB 的整段笛卡尔路径，并在路径上
采样验证可达性和关节范围。不是只有起点、终点合法就允许执行。

### 5.3 夹爪接触和抓取复核

ID6 闭合时可能因为碰到球而无法到达空载目标。程序将以下两种情况视为有效接触：

- 夹爪报告允许场景中的 `0x20` 过载；
- 夹爪位置连续多个控制周期基本不再变化，同时仍存在足够大的目标残差。

接触只对夹爪闭合、持球和释放阶段特殊处理，其他关节错误仍会中止任务。CLEAR 抬升
完成后，程序恢复摄像头并结合夹爪反馈、球是否仍在地面画面中等信息复核抓取结果。

抓取失败时，底盘保持停止，程序依次尝试小范围前后和高度偏移。重试仍失败则主动释放
夹爪并回到追球，避免机械臂带着不确定负载继续移动。启动时检测到夹爪已经夹有物体，
也会先释放再限速回 HOME。

## 6. 找桶和放球任务

### 6.1 红桶检测

抓球成功并进入 CARRY 后，状态机切换到找桶。桶不使用网球 YOLO 模型，而是在完整
640×480 RGB 图像上进行 HSV 红色区域检测，得到桶的中心、宽度和高度。随后复用与追球
相同的滤波、对齐、减速、预测制动和稳定帧控制，只是停车尺寸和速度参数独立配置。

### 6.2 高位接近、下降释放和撤离

放球使用两类互相独立的姿态：

- `PLACE_APPROACH`：程序内固定的高位、收回姿态，用于越过桶沿；
- `place_id1_deg～place_id5_deg`：配置文件给出的最终下降和释放姿态。

完整序列为：

```text
CARRY
→ PLACE_APPROACH
→ PLACE_RELEASE
→ 打开夹爪
→ 原路回到 PLACE_APPROACH
→ 回到 CARRY
→ 夹爪回到待机开度
```

接近姿态的 ID1 与最终释放方向保持一致，避免放球过程中无意义地左右摆臂。执行前会
验证最终位置至少比高位接近位置低 0.5 cm，并对所有中间关节插值点计算末端轨迹；若
轨迹低于安全走廊或向前扫出过多，`config-check` 会拒绝运行。

## 7. 机械臂为什么能够平滑运行

### 7.1 三层约束

1. `lekiwi_calibration.json` 把 0～4095 原始位置换算为关节角度，并记录机械范围；
2. `lekiwi_pick_config.txt` 定义可调目标姿态、停车条件和速度等级；
3. 任务控制器检查关节端点、可达半径和完整插值轨迹。

### 7.2 从实际位置启动

上扭矩前先读取 ID1～ID6 的实际位置，并在该位置保持扭矩，然后才限速进入目标姿态。
因此机械臂不会先跳到一个假定初始角度。动作命令也总是从反馈位置开始计算，重复执行
已经到达的姿态时可能几乎不动作，这是正常行为。

### 7.3 20 Hz 控制周期和基于时间的 S 曲线

任务控制器以 50 ms 为目标周期。每轮先读取关节反馈，计算本时刻的 S 曲线进度，再批量
写入新目标。通信耗时包含在 50 ms 周期内，不是在通信结束后额外等待 50 ms。

姿态插值使用五次平滑曲线：

```text
s(t) = 10t³ - 15t⁴ + 6t⁵，0 ≤ t ≤ 1
joint(t) = start + s(t) × (target - start)
```

曲线在起点和终点的速度、加速度都为 0，因此不会以固定速度突然起步或突然停止。
进度 `t` 由单调时钟的真实时间决定。若某一轮通信或调度变慢，整个动作可以延长，但
每周期发送给舵机的角度增量仍受速度等级限制，不会为了追赶计划突然发出大角度跳变。

动作完成也不是只看计时结束。控制器继续读取反馈，检查最大关节残差、末端几何误差、
稳定持续时间和硬性超时。负载下关节可能存在几度静差；只要末端进入安全任务区域并
稳定，允许在硬上限内完成，避免机械臂已经稳定持球却因为很小的静差频繁报错。

## 8. 机械臂动作期间的摄像头策略

抓球和放球阶段由机械臂反馈推进，不使用连续视觉控制。摄像头与 Feetech CDC 又共享
USB 路径，因此程序在进入 `PICK_BALL` 或 `PUT_BALL` 前暂停 UVC stream，动作结束后
在原设备句柄上重新建立 stream handle。

这不会重新枚举摄像头，也不会再次执行 10 帧预热。暂停和恢复各需数百毫秒，但可以
把 StarryOS 机械臂控制的历史最坏周期从约 213 ms 降到约 50 ms，避免摄像头流量挤压
舵机反馈和控制周期。

## 9. Linux 与 StarryOS 的设备后端

视觉、推理、状态机和控制代码在 Linux 与 StarryOS 中保持一致。Feetech `auto` 后端
按以下顺序打开设备：

1. 枚举 CDC ACM 设备并尝试 userspace libusb CDC；
2. 若该方式不可用，则尝试 `/dev/ttyACM0` TTY。

Linux 可以按权限和驱动状态使用任一方式。StarryOS 不依赖 `/dev/ttyACM0`，使用
libusb CDC 的控制接口、数据接口和 bulk 端点传输 Feetech 协议包。CDC 后端会消费
写入 ACK、丢弃不属于本次事务的旧状态包，并在进程退出时释放接口。

## 10. 多核环境中的实际分工

用户程序没有固定的“摄像头 CPU”和“NPU CPU”，也没有默认绑核。图像解码、NPU 调用、
后处理和控制仍由主循环按顺序推进。多核主要允许系统同时执行 USB 事件、中断、内核
任务和其他后台工作。

固定绑核的历史实验虽然提高过部分视觉样本帧率，却使机械臂最坏控制周期变长，因此
没有作为默认配置保留。以后若引入图像生产者/消费者队列，需要同时验证图像年龄、控制
延迟、USB 公平性和机械臂 20 Hz 周期，不能只比较 FPS。

分阶段性能数据和瓶颈分析见 [性能与实测数据](performance.md)。
