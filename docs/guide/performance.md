# 性能与实测数据

本文给出同一份程序在 Linux、StarryOS 及其 AxVisor 单核客户机中的同版本追球吞吐
数据，分析主要瓶颈，并汇总已验证有效的优化手段。

## 概述

- **Linux 原生和 Linux 客户机均跑满 30 FPS**，瓶颈是摄像头帧率，不是 NPU
- **StarryOS 稳态约 15～16 FPS**，瓶颈在 USB 事件调度而非传感器或 NPU 硬件
- **单核 AxVisor 客户机不会破坏视觉路径**：Linux 客户机与原生性能持平，StarryOS
  客户机与 StarryOS 原生处于同一区间
- **640×480 模型替代 640×640** 是收益最大的单项优化：NPU 时间减少 60% 以上
- **暂停 UVC 后机械臂控制周期从 213 ms 降至 50 ms**，是稳定性改善的关键操作

## 1. 测量方法与数据边界

以下数据于 2026-07-31 在同一台 RK3588 三轮机器人上复测。四种环境共用：

- Release + Warn 编译的 `build/tennis`
- 同一个 640×480 ReLU INT8 RKNN 模型
- UVC 640×480 MJPEG @ 30 FPS
- `RKNN_CORE_MASK=0`（NPU 单核模式）
- 状态日志间隔 3000 ms，性能统计窗口 10 s
- 底盘架起，摄像头视野中有球，执行正式 `lekiwi` 追球路径

每组先排除初始化/预热影响的首个窗口，再取完整 10 s 稳态窗口。Linux 各取 3 个
窗口，StarryOS 各取 2 个窗口并求平均。日志通过串口或终端前台观察，未在板端
实时重定向到文件。

> **数据边界说明**：这些是追球稳态吞吐数据。测试包含真实摄像头、JPEG、NPU、
> 后处理、底盘控制和舵机初始化，但因底盘架起且不要求真实抓球，不能用来计算
> 抓取成功率或单轮任务耗时。

## 2. 四种环境的性能对比

### 2.1 分阶段耗时

| 环境 | 客户机 vCPU | effective | wait | jpeg_decode | rknn_run | control | 单帧总时间 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 原生 Linux | 原生多核 | 29.98 FPS | 16.05 ms | 4.51 ms | 12.04 ms | 0.109 ms | 33.35 ms |
| AxVisor Linux 客户机 | 1 | 29.97 FPS | 15.66 ms | 4.82 ms | 12.07 ms | 0.114 ms | 33.36 ms |
| 原生 StarryOS | 原生 SMP8 | 15.08 FPS | 30.47 ms | 8.50 ms | 16.44 ms | 4.29 ms | 62.85 ms |
| AxVisor StarryOS 客户机 | 1 | 16.32 FPS | 29.06 ms | 8.58 ms | 17.05 ms | 1.51 ms | 59.41 ms |

### 2.2 各窗口原始值

| 环境 | 完整稳态窗口 effective |
| --- | --- |
| 原生 Linux | 29.95、30.00、29.99 FPS |
| Linux 客户机 | 29.95、30.00、29.96 FPS |
| 原生 StarryOS | 15.14、15.01 FPS |
| StarryOS 客户机 | 16.19、16.44 FPS |

### 2.3 解读

**Linux（原生和客户机）**：每轮约 33.35 ms，已经达到 30 FPS 摄像头的物理上限。
继续单独减少 NPU 的 1～2 ms 不会让整体帧率超过 30 FPS，只会留下更多 CPU 空闲。
Linux 客户机的表现与原生 Linux 几乎完全一致，说明单核 AxVisor 客户机没有对视觉
路径引入可测量的开销。

**StarryOS（原生和客户机）**：每轮约 59～63 ms。StarryOS 客户机样本（16.19、
16.44 FPS）略高于原生样本（15.14、15.01 FPS），但窗口数有限，且控制分支和
USB 调度存在抖动，不能据此宣称虚拟化比原生更快。可靠结论是：**单核 AxVisor
客户机没有破坏完整视觉路径**，StarryOS 仍处于 15～16 FPS 区间。

> Linux 客户机启动阶段仍可能出现 GICv3 ITS/MSI 警告和明显等待。这属于客户机
> PCIe 中断建立问题，与用户态程序稳态性能无关。表中数据从 Linux 完成启动并进入
> 应用稳态后开始统计。

## 3. 瓶颈分析

`effective` 是最重要的指标——它表示一秒内完整完成"取帧→解码→推理→控制"的帧数。

StarryOS 与 Linux 的差距（约 15 vs 约 30 FPS）主要来自四个环节：

| 环节 | StarryOS 耗时 | Linux 耗时 | 差距 |
| --- | ---: | ---: | ---: |
| 取帧等待 | 29～30 ms | 约 16 ms | ~14 ms |
| JPEG 解码 | 约 8.5 ms | 约 4.5 ms | ~4 ms |
| RKNN 推理 | 16～17 ms | 约 12 ms | ~5 ms |
| 控制与调度 | 1.5～4.3 ms | 约 0.1 ms | 明显波动 |

**根本原因**：StarryOS 的 `rknn_run()` 路径含 CPU 忙轮询。NPU 工作期间 CPU/调度器
没有像 Linux 那样充分让出时间给 USB 事件路径。摄像头虽然一直在后台曝光，但完整
USB 帧未能及时交付给前台——主循环完成推理后仍需等待剩余传输和调度。这是 StarryOS
与 Linux 稳态差距中最值得继续优化的系统路径。

## 4. 已验证有效的优化

### 4.1 640×480 模型替代 640×640（收益最大）

输入元素和 YOLO 候选点均减少 25%，同时消除了上下各 80 像素的无效补边：

| 项目 | 640×640 | 640×480 |
| --- | ---: | ---: |
| 输入元素 | 1,228,800 | 921,600 |
| 候选点 | 8,400 | 6,300 |
| RKNN 模型大小 | 4,676,305 B | 4,107,848 B |

严格对照测试中，Linux NPU 时间从 42.05 ms 降至 16.22 ms，StarryOS 从 93.98 ms
降至 19.84 ms。模型使用 Roboflow 数据集验证图片做 INT8 校准，已完成 Linux 和
StarryOS 实机闭环验证。

### 4.2 ReLU 激活函数替代 SiLU

同场景正式流程对比中，StarryOS SiLU 模型为 13.65 FPS，ReLU 模型为 14.11 FPS，
提升 3.4%。后续观测到的约 16 FPS 来自另一批次正常运行复测，中间没有可归因的新
吞吐修改——不能把 14.11→16.05 写成又一次优化收益。

### 4.3 UVC 完整帧获取 + 固定帧率

主线程通过 `uvc_stream_get_frame()` 直接取得下一张可用的完整图像，并关闭曝光优先
导致的动态降帧。摄像头和 USB 始终在后台持续工作；图像尚未就绪时主线程等待，而非
空转占用 CPU。

StarryOS 的 UVC-only 实测从约 11 FPS 提升到 27.6 FPS。这证明摄像头和 USB 链路本身
接近 30 FPS，正式流程的 15～16 FPS 不是传感器硬件上限，而是 NPU、解码、USB 事件
调度共同作用的结果。

### 4.4 模型先于摄像头初始化

旧顺序先启动 UVC 再执行 RKNN 大块内存分配，StarryOS 中两者竞争 USB/内存和调度，
启动到视觉就绪需要 17.54～27.67 s。改为先加载模型和分配 NPU 内存再启动摄像头后，
实测降至 1.46～1.52 s。

### 4.5 机械臂期间暂停 UVC

机械臂动作期间不消费视觉帧，继续传输只会增加 USB 竞争。暂停 UVC 后 StarryOS 机械臂
最坏控制周期从约 213 ms 降至约 50 ms，接近 20 Hz 目标。暂停和恢复各需数百毫秒，
但发生在不使用视觉的动作阶段，换来了明显更流畅和稳定的轨迹。

## 5. 性能测试注意事项

- 使用 Release 构建；StarryOS 对高频串口和文件系统日志敏感，推荐 Warn 级别
- 至少运行到两个完整 10 s 稳态窗口，排除预热、首次内存分配和机械臂回 HOME
- 只比较同一模型、场景、NPU core、日志级别和状态分支的数据
- 不要把实时日志重定向到 StarryOS 板端文件；在主机串口前台采集结果
- `camera`、`effective` 和 `busy` 含义不同，完整程序帧率以 `effective` 为准
- FPS 不能代表机械臂流畅度；还要检查 50 ms 控制周期、P95/最大延迟和动作视频
