# 双客户机控制流程、CI 完成协议与验证边界

这项 CI 是实体板集成回归测试，用来发现更新后“能够启动，但感知变慢、IVC 协作异常或
执行器未完成”的问题。它把真实感知性能、跨客户机通信和受控硬件反馈作为同一条验收链，
补足单元测试对真实设备和系统装配的覆盖。

本文描述当前 Linux/Starry + Zephyr 实现。历史拆分说明见
[AKA_RK3588_MODIFICATIONS.md](../AKA_RK3588_MODIFICATIONS.md)；运行入口见
[根 README](../README.md#axvisor-双客户机完整捡球)，控制镜像构建见
[Zephyr README](../zephyr/orangepi_robot_control/README.md)。

## 1. 双客户机如何协作

每次启动一组 Linux + Zephyr 或 StarryOS + Zephyr。

| 所有者 | 责任 |
| --- | --- |
| AxVisor | 启动两台客户机、分配设备与核心、提供 IVC 共享内存通信和控制台；不执行捡球状态机 |
| Linux/Starry 感知客户机 | 摄像头采集、JPEG 解码、RKNN 网球推理、红桶检测，读取本板标定与运行配置 |
| Zephyr 控制客户机 | 根据检测结果决定底盘动作，执行机械臂状态机，独占 UART6 和执行器反馈读取 |

正常数据方向为：感知结果 → IVC → Zephyr 决策 → UART6 → 舵机。
配置 ACK 和最终控制结果沿同一个双向 IVC 返回感知客户机。
IVC key 为 `0x49564301`，通道大小 64 KiB，感知消息为 48 字节
`PerceptionResultV2`，包含球/桶位置、大小、置信度、序号和时间戳。
UART6 使用 1 Mbps；机械臂 ID 为 1–6，车轮 ID 为 7–9。

启动时，Zephyr 自动运行控制应用，等待约 30 秒后初始化 UART、执行器并订阅 IVC。
感知端读取本板 `lekiwi_calibration.json` 和 `lekiwi_pick_config.txt`，使用随机 session
执行 BEGIN、9 个配置分片、COMMIT。Zephyr 逐条确认，校验完整配置后应用；BEGIN
等待总期限为 90 秒，其余每条配置交换期限为 3 秒。性能计时在配置握手和采集初始化后开始。
配置 CRC 证明两端应用的是同一份配置，不证明标定在物理上正确。

Zephyr 约每 1 ms 非阻塞轮询 IVC，排空当前队列后处理其中最新一条有效结果。
底盘决策由新结果触发，机械臂由独立的 50 ms 插值任务推进；二者通过现有控制锁
维护状态和 UART 所有权。反馈阶段每个 tick 只读取一只轮子的位置与速度。

## 2. 普通运行与 CI 的区别

### 普通运行

执行 `./run_dual_pick.sh` 后持续使用真实检测结果：

```text
HOME → 找球/对准/调整距离 → 停车 → 抓取准备 → 下探 → 合爪
     → 判断夹持 → 抬起/收臂 → 找桶/对准/调整距离
     → 停车 → 接近放置位 → 松爪 → 回收/收臂 → 重新找球
```

普通模式的夹持判断使用夹爪位置或过载反馈，是启发式判断；未判为夹持时打开夹爪、
回 HOME 后重试。普通模式不会在每个周期末执行 CI 专用的五阶段轮子验收。

约 350 ms 没有新的有效输入时，软件看门狗发出底盘停止命令。普通模式可在新输入到来后
恢复感知驱动控制；该分支不自动取消已经开始的机械臂插值。通信错误或空闲约 1500 ms 后，
应用仅在允许重新配置的状态尝试重新订阅并握手，不是任意故障下的自动恢复；FAULT 状态
不接受普通配置重置。

### 有限 CI

执行 `./run_dual_pick_ci_once.sh --min-fps 28`。Linux/Starry 采用同一门槛。

| 相对感知计时起点 | 行为 |
| --- | --- |
| 0–20 秒 | 使用真实摄像头、JPEG、NPU 和红桶检测；统计两个约 10 秒窗口，分别要求至少 28 FPS |
| 约 20–25 秒 | 继续真实推理，同时将发送给 Zephyr 的球位置替换为预设的缺失、左、右、远、近场景 |
| 约 25–39 秒 | 发送准备抓取的球场景，驱动真实机械臂执行抓取动作 |
| 约 39–44 秒 | 发送预设的桶缺失、左、右、远、近场景 |
| 约 44–62 秒 | 发送准备放置的桶场景，驱动真实机械臂执行放置和回收 |
| 控制周期完成后 | Zephyr 执行停止、正转、停止、反转、停止五个真实轮子反馈阶段 |
| 感知计时达到 62 秒后 | 查询 CONTROL_FINISH，最多再等 10 秒；期间发送最后场景维持输入 |

这些时间决定发送场景，不强制机械臂恰好在对应秒数切换状态。控制器仍依据自己的
插值、终点反馈和状态机推进。整个场景期间继续采集并运行 NPU；20 秒后的控制输入由
`apply_robot_ci_scene()` 覆盖。CI 夹持判断允许 `robot_ci_mode` 直接满足 holding，
因此不要求现场真的夹到球。前约 20 秒的真实感知消息尚未设置 CI 标志，
此时输入超时采用普通模式的停车分支；不能声称整个测试期间都在验证 CI 故障锁定。

## 3. 完成条件与失败传播

`robot_controller` 是控制状态、故障和检查位的唯一维护者。IVC 主循环在锁内读取
快照，锁外回复；定时任务不收发 IVC。CONTROL_RESULT 绑定已应用的 session 和配置 CRC，
包含 pending/success/failed、完成周期、检查位、控制状态和错误码。重复查询不重复动作。

`checks=31` 为以下五项的位掩码之和：

| 位 | 条件 |
| --- | --- |
| 1 | 完成一个控制周期 |
| 2 | 机械臂各受检阶段的终点反馈通过 |
| 4 | 周期末重新发送停车命令成功 |
| 8 | 三轮正反向速度和实际位置变化通过 |
| 16 | 最终三轮停车的位置与速度联合检查通过 |

机械臂终点当前容差为 220 raw；部分夹爪闭合/携带阶段不要求夹爪达到目标位置。
轮子每阶段期限仍为 2 秒：四组完整采样约覆盖每轮 450 ms。运动要求速度方向正确
且至少 20 step/s，并且三个相邻位置增量方向正确、每段至少两个编码器刻度。
停车要求整个四组窗口的位置跨度不超过一个刻度，同时所有速度反馈均在 ±50 step/s 内。
位置按 4096 刻度回绕处理；不能把每次允许的小增量累积成持续爬行。

CI 进入故障状态后保留错误，后续成功的停车命令或新感知输入不会把本会话改为成功。
感知端只有收到当前会话的完整控制成功结果，完成摄像头关闭、JPEG 解码器关闭、模型释放
和 IVC 关闭后，才输出唯一的 `DUAL_PICK_APPLICATION_PASS`。脚本验证记录、性能窗口、
完成时长及进程退出码；board 入口还需 `sync` 成功，才输出独占一行的
`DUAL_PICK_CI_PASS guest=...`。中间日志及 Shell 命令回显都不构成最终成功。

| 可被判为失败的情况 | 当前判据 |
| --- | --- |
| 启动或配置失败 | 设备/模型初始化失败，配置拒绝、无有效 ACK、握手超时；外层还有板卡超时 |
| 感知调用失败 | RKNN 输入、推理、输出获取/释放等返回错误；CI 中推理错误直接失败 |
| 采集/解码持续失败 | 连续失败达到 10 次退出；较少的坏帧剔除并计数，不计入推理 FPS |
| 性能不足 | 两个约 10 秒窗口中任意一个有效 FPS 小于 28 |
| IVC 异常 | 发送失败、发送端重试耗尽产生丢帧、无当前会话的有效完成回复或回复失败 |
| 执行器异常 | UART 超时/校验/未允许的设备状态错误、机械臂受检终点超差、轮子反馈不满足上述规则 |
| CI 输入断流 | 收到带 CI 标志的场景、进入 robot_ci_mode 后，未完成时断流约 350 ms，触发停车并锁定失败 |
| 不完整结束 | 提前退出、中断、清理返回错误、控制未完成、旧 checks=7、缺失/重复最终记录、非零退出或 sync 失败 |

## 4. 不能据此证明什么

- **识别准确率和图像新鲜度**：没有标注图像的准确率对照，也没有静帧/遮挡检测；
  推理成功不等于识别正确，后半段预设场景也不能证明真实视觉闭环正确。
- **真实抓球、搬运和投桶成功**：CI 可以模拟 holding；普通模式的位置/过载启发式
  也不能证明球未掉落、已正确放进桶。
- **地面运动和全程运动质量**：轮子编码器有运动不等于底盘按预期位移，不能判断
  打滑、轮子装配映射错误、路径偏差、碰撞或载荷下行为；机械臂终点检查不是连续轨迹、
  力矩或高精度位置验收。专门的低速正反转检查不逐一验证全部底盘运动组合。
- **每帧送达与处理、严格新鲜度**：`ivc_dropped=0` 是发送端指标。接收端允许合并为
  最新队列项，少量非法感知包会丢弃计数，并不单独强制 CI 失败。当前没有按消息时间戳
  严格限制帧龄，也没有检查感知序号单调递增；持续到达的旧内容可能继续重置输入看门狗。
- **硬实时和硬件急停**：350 ms 是软件触发阈值，动作受调度、锁和 UART 影响；若 Zephyr、
  宿主或总线本身失效，不保证物理停车。正向 CI 没有系统化执行拔线、断电或卡死故障注入。
- **全天性能与全部平台**：只门禁前两个性能窗口，不要求后续每个窗口持续达标；
  三次冷启动不能替代 24 小时压力、P99/最大端到端延迟或其他板卡/镜像的验证。
- **所有故障的物理根因**：能报告失败阶段和部分错误码，不一定区分供电、接线、
  驱动、机械卡阻；共同错误但自洽的传感器反馈也缺少独立真值校验。

2026-09-20 的本轮实体板验证为 eMMC 机器人：Linux+Zephyr、Starry+Zephyr 各三次冷启动
通过同一套 28 FPS 和完整反馈门禁；不能扩大为 SD CI 板已复验。异常状态机判定另有
host/native_sim 的确定性失败/通过对照，与实体硬件故障注入分开记账。
